# llama.cpp for OpenCL 1.1 (CL11 backend)

The CL11 backend runs ggml graphs on GPUs that only offer **OpenCL 1.1**. The targets are the
NVIDIA GeForce GT 430 (Fermi, compute capability 2.1), GT 730 and GT 710 (Kepler GK208, compute capability 3.5), all with the
driver 390.x (`Device Version: OpenCL 1.1 CUDA`), but it works on any
OpenCL GPU: it is a separate backend, the existing `GGML_OPENCL` backend (Adreno / Intel, OpenCL >= 2.0)
is not touched and both can be enabled at the same time. AMD GPUs work through Mesa Clover (OpenCL 1.1) and Mesa rusticl (OpenCL 3.0): the
Radeon Pro WX 2100 (Polaris 12, GCN) is tuned, see "AMD Radeon Pro WX 2100" below, and the Radeon RX 6400 (RDNA2) works with the settings that every AMD GPU shares
(rusticl; Clover hangs the GPU there). The official Vulkan backend is faster on both Radeons, use it when it works.

What "OpenCL 1.1 only" means here:

- host code: C API of OpenCL 1.1 only (`CL_TARGET_OPENCL_VERSION 110`), no `cl2.hpp`; no
  `clEnqueueFillBuffer`, `clEnqueueMarkerWithWaitList`, `clCreateProgramWithBuiltInKernels`, images, SVM, ...
  (memset is done by a kernel),
- device code: OpenCL C 1.1 (`-cl-std=CL1.1`), no `cl_khr_fp16` (`vload_half` / `vstore_half` only), no
  `double`, no sub-groups,
- the work-group sizes are not hard coded: they start from `CL_DEVICE_MAX_WORK_GROUP_SIZE` (capped to 128 for
  the 1-D kernels and 16x16 for the matrix-matrix kernel) and are reduced, rebuilding the program, until every
  kernel accepts them (`CL_KERNEL_WORK_GROUP_SIZE`).

## Build

The ggml backend of CL11 lives in `adapters/ggml/` of ScrapGpuLibrary (the OpenCL 1.1 runtime and the kernels are in `src/backends/opencl11/`) and is written for llama.cpp b11384 (commit 0faee50); the ggml
backend API is not stable. It is built either as an out-of-tree plugin (llama.cpp is not modified) or in-tree
(a 15-line patch); the details are in [adapters/ggml/llama.cpp/README.md](../adapters/ggml/llama.cpp/README.md).

Out-of-tree plugin (llama.cpp built once with `-DGGML_BACKEND_DL=ON -DBUILD_SHARED_LIBS=ON`):

```bash
cmake -S adapters/ggml -B build-cl11 -DLLAMA_CPP_SOURCE_DIR=<llama.cpp> -DLLAMA_CPP_BUILD_DIR=<llama.cpp>/build-dl
cmake --build build-cl11 -j
GGML_BACKEND_PATH=$PWD/build-cl11/libggml-cl11.so <llama.cpp>/build-dl/bin/llama-bench --list-devices
```

In-tree (the script copies the sources and applies the patch):

```bash
adapters/ggml/llama.cpp/install-in-tree.sh <llama.cpp>
cd <llama.cpp>
cmake -B build-cl11 -DGGML_CL11=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-cl11 -j --target llama-cli llama-bench test-backend-ops
```

The kernels (`src/backends/opencl11/kernels/*.cl`) are embedded as strings by CMake at configure time (no Python
needed); cmake re-runs when a `.cl` file changes.

Requirements: an OpenCL ICD loader and the OpenCL headers (`ocl-icd-opencl-dev opencl-headers` on Debian/Ubuntu,
the NVIDIA 390 driver provides the ICD). On macOS the system OpenCL framework is used (OpenCL 1.2, deprecated by
Apple but fine for development).

Linux build for a Fermi machine (no other GPU backend, CPU backend tuned for the host), in-tree:

```bash
cmake -B build-cl11 -DGGML_CL11=ON -DGGML_NATIVE=ON -DLLAMA_CURL=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build-cl11 -j --target llama-cli llama-server llama-bench test-backend-ops
```

The commands in the rest of this document use the in-tree build directory `build-cl11`; with the plugin, run the
llama.cpp binaries of the `GGML_BACKEND_DL` build with `GGML_BACKEND_PATH` set.

## Usage

Devices are named `CL11_0`, `CL11_1`, ... (all GPU devices of all OpenCL platforms) and the description is the
OpenCL device name:

```bash
./build-cl11/bin/llama-cli --list-devices
./build-cl11/bin/llama-cli -m model.gguf -dev CL11_0 -ngl 99 -p "Hello" -n 64
./build-cl11/bin/llama-bench -m model.gguf -dev CL11_0 -ngl 99
```

or graph); listing the devices does not build anything. The first start builds the kernels (a few seconds).

## Design notes

- Tensors are addressed as offsets from a dummy base pointer; the kernels get a `cl_mem` plus a byte offset
  (no sub-buffers, so no sub-buffer alignment constraints). `get_max_size` is `CL_DEVICE_MAX_MEM_ALLOC_SIZE`
  (limited to 2 GiB because the kernels use 32-bit offsets), ggml-alloc splits the model and the compute buffers
  into several buffers.
- The whole graph is enqueued on one in-order command queue; the host only waits in `synchronize()` and
  `get_tensor()` (and `set_tensor()` is a blocking write, which also waits for the queue). There is no `clFinish`
  per node.
- All kernels are launched as 2-D NDRanges (`x` <= 32768 work-groups) and linearize the group index
  themselves, so no grid dimension exceeds 65535 (Fermi limit, e.g. for the 151936 rows of an output matrix).
- `MUL_MAT` with `ne11 <= GGML_CL11_MV_MAX_COLS` uses a mat-vec kernel per type of src0, otherwise a tiled mat-mat
  kernel: a work-group of `(gt/2) x (mm_bn*gt/4)` work-items computes a `(4*gt) x (mm_bn*gt)` dst tile (64 x 128 by default, 64 x 64 on Kepler),
  every work-item accumulates 8 x 4 values with 128-bit local memory loads (3 loads per 32 FMAs), BK=16, src0 is dequantized
  while it is copied to local memory (the repacked weights: one coalesced 16-byte load per row and step, scale (and min) applied
  while the tile is written; F32 / F16 element by element) and src1 is copied with 128-bit loads when it is 16-byte aligned.
  Computation is F32 (src1 is not quantized, so the results are closer to the exact product than the CPU backend which
  quantizes src1). The mat-vec kernels are described in "Performance".
- **Q4_0 / Q8_0 / Q4_K / Q6_K weights are stored in a repacked layout** ("R32", property of the tensor: `cl11_repacked()`): the blocks of
  18 / 34 / 210 bytes are only 2-byte aligned (144 bytes for Q4_K), and all of them mix several fields, so the natural layout can only be read
  with 16-bit loads and a lot of address arithmetic. `set_tensor` converts the weights when they are uploaded and `get_tensor` converts them
  back (the size is the same as `ggml_nbytes()`, partial reads / writes work, a view of such a tensor is not supported). For every slice of
  the tensor (`ne2*ne3` slices of `M = ne1` rows, `nb` blocks per row) the rows are grouped by 32; inside of a group of `rs` rows (32,
  fewer for the last group) the bytes of a block are split into up to 3 "areas" (one after the other in the slice, area `k` starts at
  `M * nb * (bytes per block of the areas before it)`); an area made of 16-byte units holds, for the block `b` of the row `lane` of the
  group, the unit `j` at `(b * U + j) * rs + lane` (`U` = units per block), so that a warp (one row per lane) reads 512 contiguous bytes
  with 128-bit loads; the half scales are stored apart:

  | type | areas (bytes per block) |
  | --- | --- |
  | Q8_0 | quants 32 (2 units, xor 0x80) \| d (half) |
  | Q4_0 | nibbles 16 (1 unit) \| d (half) |
  | Q4_K (256 weights) | quants 128 (8 units: the 128 bytes of nibbles) \| header 16 (1 unit: d, dmin, the 12 bytes of 6-bit scales and mins) |
  | Q6_K (256 weights) | ql + qh 192 (12 units) \| 16 int8 scales (1 unit, xor 0x80) \| d (half) |

  Tensors that cannot be repacked (not contiguous, views, slices whose size is not a multiple of 16 bytes) are not supported
  by CL11 (`supports_op` is false, the CPU backend is used): the permuted / strided Q4_0 / Q8_0 / Q4_K / Q6_K `MUL_MAT` and `GET_ROWS` cases of
  `test-backend-ops` that were supported before are now "not supported" (1985 -> 1957 -> 1937 supported cases).
- FLASH_ATTN_EXT is not supported: the `auto` setting of llama.cpp disables Flash Attention
  (`resolve_fused_ops: Flash Attention not supported, set to disabled`), the V cache is transposed and
  `SET_ROWS` writes it.
- Fully offloaded llama/qwen2/qwen3 graphs run with 2 splits (the token embedding `GET_ROWS` of the input layer
  stays on the CPU, everything else is on CL11). The same holds for LFM2 and LFM2-MoE (see "MoE and hybrid models").

## Supported operations

`supports_op` returns true only for the combinations below, they all pass `test-backend-ops`; everything else
falls back to the CPU backend.

| op | types / conditions |
| --- | --- |
| `NONE`, `RESHAPE`, `VIEW`, `PERMUTE`, `TRANSPOSE` | nothing to compute |
| `MUL_MAT` | src0 `F32`/`F16` (rows contiguous, may be a permuted view such as the KV cache), `Q4_0`/`Q8_0`/`Q4_K`/`Q6_K` (a whole contiguous tensor, see "Design notes"), src1 `F32` (rows contiguous, any other strides), dst `F32`; broadcast `ne12 % ne02 == 0`, `ne13 % ne03 == 0` (GQA) |
| `GET_ROWS` | src0 `F32`/`F16`, `Q4_0`/`Q8_0`/`Q4_K`/`Q6_K` (whole contiguous tensor), idx `I32`, dst `F32` |
| `SET_ROWS` | src `F32`/`F16`, idx `I64`/`I32`, dst `F32`/`F16` |
| `ADD`, `SUB`, `MUL`, `DIV` | `F32`, src1 broadcast along every dimension, arbitrary strides |
| `SCALE` (scale and bias), `CLAMP`, `SQR`, `SQRT` | `F32` |
| `UNARY` | `SILU`, `RELU`, `NEG`, `ABS`, `SIGMOID`, `TANH` on `F32` |
| `GLU` | `SWIGLU`, `REGLU` on `F32`, fused (halves of src0, `swapped`) and split (src0, src1) |
| `RMS_NORM` | `F32` |
| `ROPE` | normal and NEOX, `F32`/`F16`, yarn parameters, `freq_factors`, `n_offs`; no mrope / vision |
| `SOFT_MAX` | `F32`, optional mask `F32`/`F16` (broadcast along dims 2, 3), `scale`; no ALiBi (`max_bias != 0`), no sinks |
| `CPY`, `DUP`, `CONT` | `F32`/`F16` to `F32`/`F16`, arbitrary strides and shapes |
| `MUL_MAT_ID` | experts (src0, 3-D `[K, M, n_expert]`) `F32`/`F16` (rows contiguous, may be a strided view) or `Q4_0`/`Q8_0`/`Q4_K`/`Q6_K` (a whole contiguous tensor, see "Design notes"), src1 `F32` with 1 or `n_used` columns per token, ids `I32`, dst `F32`; `ne03 = ne13 = 1`; the scratch buffers of the prompt path (`n_used * n_tokens * max(K, M)` floats) must fit in one buffer. See "MoE and hybrid models" |
| `ADD_ID` | `F32` (bias of an expert), ids `I32` |
| `SSM_CONV` | `F32`, `src0` `[d_conv - 1 + n_t, d_inner, n_s]` with contiguous rows (other strides are fine) |
| `CONCAT` | any dimension, 4-byte (`F32`, `I32`) and 2-byte (`F16`, `BF16`, `I16`) elements, any strides |
| `PAD` | `F32`, `ggml_pad_ext` (any padding on every dimension) and `ggml_pad_ext_circular` |
| `SUM_ROWS` | `F32`, any strides |
| `ARGSORT`, `TOP_K` | `F32` keys, `I32` result, ascending or descending; the row is sorted in local memory, so `ncols` rounded up to a power of 2 times 8 bytes (+ 512) must fit in `CL_DEVICE_LOCAL_MEM_SIZE`: 2048 columns on a 32 KiB device (Apple M2), 4096 on a 48 KiB device (Fermi / Kepler), 8192 on 64 KiB. Longer rows (a sampler over the vocabulary) are left to the CPU |

Not supported (CPU fallback): `FLASH_ATTN_EXT`, `NORM`, `GROUP_NORM`, `SSM_SCAN` / RWKV ops, other quantization types (`Q4_1`, `Q5_x`,
`IQ*`, ...; also as the experts of `MUL_MAT_ID`), `BF16` weights, copies into quantized types, `ARGSORT` / `TOP_K` of rows longer than the limit
above, ...

## MoE and hybrid models (LFM2, LFM2-MoE)

LFM2 mixes short convolution layers (`CONCAT` of the conv state and the new tokens, `SSM_CONV`, `CPY` of the new state) with attention layers, LFM2-MoE
(e.g. LFM2.5-8B-A1B: 32 experts, 4 used per token) replaces the FFN by a mixture of experts: router (`MUL_MAT`, `SIGMOID`, `ADD` of the selection bias),
`ARGSORT` (descending, `ggml_argsort_top_k` is a view of it), `GET_ROWS` of the probabilities (3-D indices), `SUM_ROWS` / `CLAMP` / `DIV` / `SCALE`
(normalization of the weights), three `MUL_MAT_ID` (up, gate, down), `SWIGLU`, `MUL` by the weights and the `ADD` of the `n_used` views. All of these are
supported, so the whole graph (except the token embedding `GET_ROWS` of the input layer) runs on CL11 in 2 splits. `GGML_CL11_LOG_UNSUPPORTED=1` prints
every operation that is left to another backend.

**MUL_MAT_ID** computes `dst[:, i, t] = experts[:, :, ids[i, t]] * src1[:, i % ne11, t]`. The experts are one 3-D tensor `[K, M, n_expert]`; the repacked
layout "R32" is per slice (`ne2 * ne3` slices, see "Design notes"), so expert `e` is the slice at `e * nb[2]` and `cl11_repacked()` only needs
`nb[2] % 16 == 0` (always true for Q4_K; for Q4_0 / Q8_0 / Q6_K when `M * K / block_size` is a multiple of 8, which holds for real models). There are two methods:

- *Generation* (`n_used * n_tokens <= n_expert`, so one token always; `GGML_CL11_MID_MAX_TOKENS=<n>` uses it up to `n` tokens instead): one launch for
  all the selected experts and no synchronization. Above that it would read more weights than the whole expert tensor holds. The kernels are the
  mat-vec kernels of `MUL_MAT` (`k_mvri_q4_0` / `k_mvri_q8_0` in `mul_mv_r.cl`, `k_mvki_q4_k` / `k_mvki_q6_k` in `mul_mv_k.cl`, `k_mvi_f32` / `k_mvi_f16` in
  `mul_mv.cl`: the same loops, built with another definition of the macro that selects the slice of src0) with dst as the grid `[M, n_used, n_tokens]`:
  the work-group of (row tile, slot, token) reads the expert number from the ids (`I32`, any `nb[1]`, clamped to the number of experts) itself and
  reads the slice `ids[slot, token]` of src0. src1 with one column per token is shared by the slots (stride 0). It needs the same alignment as the
  mat-vec of `MUL_MAT` (16 bytes); if that fails, or `GGML_CL11_MV_MAX_COLS=0`, the prompt method is used.
- *Prompt processing* (more tokens): the ids are read back to the host (`clEnqueueReadBuffer`, which waits for the queue: one synchronization per
  `MUL_MAT_ID`, 3 per layer), the (slot, token) pairs are sorted by expert, `k_mid_gather` copies the columns of src1 of all the pairs in that order into a
  scratch buffer, every expert that is used computes its range of columns with the normal `MUL_MAT` kernels (`cl11_mul_mat_core`: the mat-mat
  kernel, or the mat-vec kernel for a single column) on the slice of the weights, and `k_mid_scatter` copies the result columns into dst. The scratch
  buffers (gathered columns, results, pairs) are plain `cl_mem` objects that grow when needed and stay allocated. This was written for correctness: the
  launches are `2 + n_experts_used_by_the_batch` per node, and the synchronization stalls the pipeline; routing on the device (counting the tokens
  per expert with atomics and one grouped mat-mat) is not done.

With the experts on the CPU (`--cpu-moe`, or `-ot "ffn_.*_exps=CPU"`, which is what a card with too little memory needs) the router, the `ARGSORT`
and everything else stay on CL11 and only the three `MUL_MAT_ID` of a layer run on the CPU (2 splits become 46 for LFM2.5-8B-A1B).

**ARGSORT / TOP_K**: one work-group per row; the row is padded to a power of 2 with `-inf` (`+inf` ascending) and sorted in local memory
(`float` keys + `int` indices, 8 bytes per element) by a bitonic network. Equal keys are ordered by index, so the result is deterministic and the padding
never gets into the first `ncols` entries. That is why `supports_op` needs `8 * pow2ceil(ncols) + 512 <= CL_DEVICE_LOCAL_MEM_SIZE`. `TOP_K` is the same
kernel that writes only the first `k` indices (sorted, which the op does not require). The result can differ from the CPU for equal keys (the CPU's
`std::sort` is not stable either); `test-backend-ops` compares ties by value.

`GGML_CL11_NO_OPS=NAME,NAME` (the names of `ggml_op_desc`, e.g. `MUL_MAT_ID,ARGSORT`) makes `supports_op` false for those operations: a way to test mixed
CPU / GPU graphs.

**Measured on the TB250** (LFM2.5-8B-A1B Q4_0, `llama-completion -n 128 -c 1024 -t 2`, greedy, CL11 with `--cpu-moe`; one GPU per run with `GGML_CL11_DEVICES`;
the three GPUs of the table, the Radeon RX 6400 with the official Vulkan build b11384 for comparison):

| configuration | tg (t/s) |
| --- | --- |
| CPU only (`-dev none -ngl 0`, Celeron G3930) | 6.3 |
| GT 430, `--cpu-moe` | 10.4 |
| GT 710, `--cpu-moe` | 8.8 |
| GT 730, `--cpu-moe` | 11.7 |
| RX 6400, Vulkan, `--cpu-moe` | 12.0 |
| RX 6400, Vulkan, `--n-cpu-moe 8` | 21.0 |

With the experts on the CPU, the three `MUL_MAT_ID` of a layer on the CPU (about 80 ms per token) are the limit, not the GPU: the GT 430, 710 and 730 get 8.8 - 11.7 t/s
although they differ by 2x in memory bandwidth. Putting the experts of more layers on the GPU helps only when the GPU is fast enough: on the GT 710 (2 GiB, 14.4 GB/s) `--n-cpu-moe 18` and `20` give the same
8.9 and 8.8 t/s as `--cpu-moe`. The greedy output (the prompt of "Validation status") is not the CPU's: the GT 710 and the GT 730 differ from the CPU from about the 300th byte on (the order
of a list of countries), the GT 430 from the 3rd generated token on ("city name length: 5 letters ..."), the same text as the Mac with `--cpu-moe`; all are coherent near-tie flips of the router, see
the KL divergence in "Validation status" (the GT 430 is not worse than the others).

**Out of device memory.** The NVIDIA 390 driver does not take the memory in `clCreateBuffer`: a buffer that does not fit is accepted and the first kernel or transfer that touches it fails with
`CL_MEM_OBJECT_ALLOCATION_FAILURE`. `ggml_backend_buffer_clear()` and `set_tensor()` cannot return an error, so the plugin used to `GGML_ABORT` (a GT 710 with
`--n-cpu-moe 16`: `ggml-cl11.cpp: ggml_backend_cl11_buffer_clear: clear failed`, rc 134). Now `alloc_buffer` writes the last 16 bytes of **every** new buffer (one blocking transfer, which makes the
driver allocate all of it; the same probe the buffers above `CL_DEVICE_MAX_MEM_ALLOC_SIZE` had) and returns `nullptr` when that fails, as the scratch buffers of the prompt method of `MUL_MAT_ID` do. llama.cpp then ends
with an error message instead of an abort (GT 710, `--n-cpu-moe 16`, `-ub 128`: `failed to allocate CL11_0 buffer of size 12582912` / `failed to allocate buffer for kv cache`, rc 1;
`--n-cpu-moe 15`: `unable to allocate CL11_0 buffer` while loading the model). `-fit` (the default of llama.cpp, when `-ngl` / `-ot` are not given) works on the same numbers (`get_memory` reports the
total minus 128 MiB): on the GT 710 `llama-completion` without `-ngl` puts all 25 layers on the GPU, 22 of them without their experts (in system memory), and generates (8.7 t/s).
The largest number of expert layers that fit on the 2 GiB of the GT 710 with `-c 1024`: `--n-cpu-moe 17` with `-ub 128 -b 128` (the experts of 7 of the 24 layers on the GPU; tg 8.87 t/s),
`--n-cpu-moe 18` with the default `-ub 512` (8.87 t/s; with 17 the 260 MiB compute buffer of the prompt graph does not fit: `failed to allocate compute pp buffers`).

## Limitations

- `get_max_size` is the nominal `CL_DEVICE_MAX_MEM_ALLOC_SIZE` (241 MiB on a GT 430), so ggml splits the model
  weights over several buffers. A **single tensor** larger than that (the logits `n_vocab x n_ubatch`, large
  compute tensors, the output / token embedding matrix of a big-vocabulary model) still needs one buffer, see the
  next section.
- `GGML_OP_SOFT_MAX` / `ROPE` / `RMS_NORM` rows must be contiguous in dimension 0.
- No `mmap` (the weights are copied to the device), no host buffers, no events, no asynchronous tensor
  copies, no multi-device split between several CL11 devices (each device has its own `cl_context`).
- `__constant` arguments that are sub-buffers (`GGML_CL11_MVR_CONST_X`) do not work on the Kepler GPUs with the NVIDIA 390 driver: the driver
  ignores the offset of the sub-buffer and reads the base of the parent buffer (wrong results). The option stays off on Kepler.
- NVIDIA 390 allocates a buffer at its first use (see "MoE and hybrid models", "Out of device memory"): `alloc_buffer` touches every new buffer to turn that into an allocation failure. Memory that
  other processes take later, or kernels that need more scratch memory than is left, still fail at the launch (`graph_compute` returns `GGML_STATUS_FAILED`).
- The same driver crashes in `clReleaseMemObject` when overlapping sub-buffers (the `__constant` columns of src1 of the mat-vec, `GGML_CL11_MVR_DN=0` on a GT 430, many different columns as in
  `llama-perplexity -b 1`) are released in the order of their creation; `free_buffer` releases the newest first.
- The Q4_K / Q6_K mat-vec kernels of NVIDIA GPUs with a register cap are compiled in a second program when the first of them is used
  (a few seconds more for the first token of a K-quant model, see "Per-GPU tuning").

## Performance

Measured on the GeForce GT 430 (Fermi, 96 cores, 2 SMs, 28.8 GB/s peak, ~22.9 GB/s measured with a plain streaming kernel,
NVIDIA 390.157, `llama-bench -ub 128 -b 128`, CPU: `-dev none -ngl 0 -t 2` of the same machine, a Celeron G3930). The reference point is
a first version whose mat-vec kernels read 2-byte pieces of the blocks and whose elementwise kernels used integer divisions:
2.97 t/s for Qwen3-0.6B Q8_0.

### What was slow (and what is done about it)

- **Integer division.** A 32-bit division or modulo expands to a long instruction sequence on Fermi (instruction count not yet measured from SASS). Decomposing a linear index
  into 4 dimensions in every work-item was more expensive than the dot product of a short row (the attention
  `MUL_MAT` of the K and V caches took 530 us instead of 140 us, a 0.5 MiB `CONT` 640 us). Every division by a
  tensor dimension is now a multiplication: the tensor descriptor (`tdesc`) carries the magic numbers for `ne0..ne3`
  (`FDIV`, `FMOD`), the mat-mat / mat-vec kernels get the broadcast ratios and the tiling constants in a `bcast`
  struct, the row kernels (RMS_NORM, SOFT_MAX, ROPE, GET_ROWS) use one work-group per row.
- **Reading src1.** With one work-group per output row the float vector src1 (4 bytes per weight) is read once per
  row, 4x the traffic of the Q8_0 weights, and the L2 of the GPU is small. The mat-vec kernels of the "x" family
  (`mul_mv_x.cl`, F32 / F16 / Q4_K / Q6_K) compute `NRW` (2) rows per warp, src1 is loaded once for the rows of the warp (`k_mvw_*`: from the
  caches, `k_mvx_*`: copied to local memory once per work-group; the local copy is only faster for q4_K). The long
  rows of F32 and F16 reach the DRAM bandwidth of the card (18.6 / 12.5 GB/s of weights).
- **Quantized blocks of 18 / 34 bytes (Q4_0 / Q8_0): the repacked layout.** The blocks are only 2-byte aligned, everything
  was read with 16-bit loads, and the address arithmetic (64-bit adds, 32-bit multiplications by 34) made the loop about 15
  instructions per weight (8.5 GB/s of Q8_0, 4.7 GB/s of Q4_0). A micro benchmark with the same access pattern but no arithmetic reads 11 GB/s, coalesced 32 / 128-bit loads read 19-23 GB/s. The weights are now stored in the "R32" layout (see "Design notes"):
  the lane of a warp is the row, a 128-bit load per lane and block half, no reduction over the lanes (the partial sums of the
  warps of a work-group, which split the blocks of a row, are added once through local memory at the end), and src1 is the same
  for all the lanes. The byte -> float conversion is the one of the other kernels (the byte is the mantissa of `2^23 + b`, one
  `prmt` on NVIDIA, the offset subtracted exactly; the bytes of Q8_0 are stored xor 0x80 so no instruction is spent on the sign).
  `k_mvr_q8_0` / `k_mvr_q4_0` (`mul_mv_r.cl`): 2 rows per lane (one src1 load for 2 rows), 2 warps per work-group, 63 registers.
- **Loads of src1.** The 8 `float4` of src1 per block and row pair are loads for the load / store units, competing with the
  weights (the mat-vec runs at about 75% of the streaming rate with them, 83% without). A single column of src1 (at most 64 KiB) is
  therefore passed as a `__constant` argument: `clCreateSubBuffer` on the tensor (aligned like all tensors, the sub-buffers are cached
  and released with the parent buffer), the loads of src1 then use the constant cache and cost no load / store instruction
  (+15% Q8_0, +30% Q4_0; `GGML_CL11_MVR_CONST_X`). Longer vectors / several columns use the global-memory kernels.
- **Attention without Flash Attention.** With `auto` the KV cache of llama.cpp keeps the V cache untransposed and
  every layer copies `transpose(V)` with a `CONT`. The tiled transposing copy kernel (`k_cpy_t_*`, 32x32 tiles through
  local memory, coalesced reads and writes) takes 136 us instead of 640 us, and `CONT` + `MUL_MAT` (decode) is
  fused: `k_mvt_f16` reads the strided view directly (110 us for both instead of 260 us). `-fa off` gives the same
  speed; `-fa on` is slower (no Flash Attention on CL11, the node runs on the CPU).
- **Mat-mat (prompt processing).** The tiled kernel had 4x4 values per work-item with scalar local memory loads (LDS-bound: 8 loads
  per 16 FMAs) and dequantized element by element. Now 8 x 4 values per work-item with 128-bit local memory loads (3 per 32 FMAs),
  64 x 128 tiles, the dequantization of the repacked tiles is one coalesced 16-byte unit per row and step, the addresses of the
  tiles are computed before the loop, the padded stride of the tile of src0 (`BM + 4`) makes the generic (element by element)
  staging of F32 / F16 / Q4_K / Q6_K conflict free (that alone: F32 49 -> 89 GFLOPS, Q4_K 12 -> 62). The same kernel without the
  compute (only the barriers and a store per step) reaches 151 GFLOPS (theoretical peak 268), so the staging is still ~35% of the time.

What was done for the Kepler GPUs:

- **K-quants in the repacked layout** (`mul_mv_k.cl`): lane = row, one 128-bit load per lane and piece of the block, the 6-bit scales and mins
  of a Q4_K super-block are converted four at a time with the `prmt` trick, the high nibbles are used without the shift (`& 0xF0F0F0F0`,
  the factor 1/16 is applied to the sum of the sub-block), the sums of src1 for the mins are computed once for the rows of the lane. The mat-mat
  kernel dequantizes one 16-byte unit per row and step (the same code as for Q4_0 / Q8_0, header kept in registers per super-block).
- **`ld.global.nc` for src1** (inline PTX, sm_35+, `CL11_NV_LDG`, `GGML_CL11_NO_LDG`): the read-only data cache has its own path and relieves the
  load / store unit; +10% for Q4_K / Q6_K, but -10% for Q4_0 / Q8_0 and -35% when it is used for the weights, so it is a per-type setting (`mvr_ldg`).
- **A second program for the Q4_K / Q6_K mat-vec kernels** (`cl11_ensure_kprogram`): `-cl-nv-maxrregcount=128` (the kernels need 100-140 registers, the
  default allocation leaves too few warps; Q4_K 56% -> 67%, Q6_K 62% -> 70-75%) makes Q4_0 / Q8_0 5-6% slower, so these kernels are built
  apart, with the option, when the first K-quant mat-vec is computed.
- **Work-group sizes and rows per lane**: 128 items (4 warps) and 2 rows per lane for Q4_0 / Q8_0 (1 row per lane for Q8_0 on the 1 SMX GT 710),
  64 items and 2 rows for the K-quants (see the table of "Per-GPU tuning" for the alternatives that were measured).
- **Mat-mat tile 64 x 64** instead of 64 x 128 (`mm_bn = 4`): +18% (GT 730) / +22% (GT 710) for the quantized types.
- **Attention kernels** (`attn.cl`), see below, and the fusion of `RMS_NORM` + `MUL` and `ADD` + `RMS_NORM` + `MUL` (one kernel instead of two or
  three: ~12 us each on the GT 710, ~2 ms per token of Qwen3-0.6B).

#### Attention kernels

The cache of llama.cpp keeps the heads of a position together (a row of the K cache: all the heads, 2 KiB for Qwen3-0.6B), the generic mat-vec
kernels read 256 bytes of every 2 KiB with a few lanes per output and were latency bound. `k_mvq_f16` (K cache, `MUL_MAT` with a F16 src0 of at most 256 columns,
a single column of src1, at most 8 query heads per head of the cache) and `k_mvt_f16` (V cache, fused with the `CONT` of the transposed view) read whole rows
of the cache with 16-byte loads (the lane is a 16-byte piece of the row) and compute the query heads that share a head of the cache together (grouped query attention);
the partial sums go through a small local memory array. Per call for the 512 KiB caches of Qwen3-0.6B (GT 710 / GT 730 / GT 430):
K 92 / 49 / 115 us (before, GT 710 / GT 430: 228 / 124 us), V 69 / 49 / 79 us (before: 130 / 113 us). A cold read of 512 KiB takes 55 us on the GT 710.
What the GT 710 (DDR3) showed:

- More than two 16-byte loads in flight per lane make the kernel *slower* (all the loads first, then the sums: 99 us for 512 KiB instead of 55 us;
  two at a time: 56 us): the DRAM page conflicts of many independent streams. The kernels load two rows at a time.
- The local memory declared for the worst case (8 query heads) limited the occupancy to one work-group per SMX (270 us): the arrays are sized for two query
  heads per pass.
- The V cache kernel has a single work-group per batch: its slices of the positions are separate warps of the same group (1024 work-items on Kepler,
  512 gave 85 us instead of 70 us; the value is limited by the kernel's resources).

#### Kepler round 3: mat-mat candidates and fewer launches (measured on the GPUs 2026-10-09)

Everything in this section was written and verified on a Mac first (see "Validation status"), then measured on the GT 730 / GT 710 / GT 430 in one run of `tools/kepler-sweep/sweep.sh`
(results below). The Kepler default is now the `x84` mat-mat kernel and the two fusions.
The two fusions are on in the Kepler branch of `cl11_tuning_for()` (off on the other generations, `GGML_CL11_MULTI_MV` / `GGML_CL11_FUSE_SET_ROWS` force them on any GPU), the
new mat-mat kernels are candidates that stay off (`GGML_CL11_MM_VARIANT` selects one) until a variant has been measured to be faster.

**Parameterized mat-mat kernels `k_mmx_*`** (`src/backends/opencl11/kernels/mul_mm_x.cl`, F32 / F16 / Q4_0 / Q8_0 / Q4_K / Q6_K like `k_mm_*`; compiled only when a variant is selected, so the other
GPUs and the default build are unchanged). They are the kernel of `mul_mm.cl` with the following parameters (compile-time defines, chosen by the host):

| key | meaning | values |
| --- | --- | --- |
| `bm`, `bn` | tile of dst: rows of src0 x rows of src1 (the default kernel: 64 x 64 on Kepler, 64 x 128 elsewhere) | multiples of `rm` / `cn` |
| `rm`, `cn` | values per work-item: `rm` rows (float4 groups) x `cn` columns; the work-group has `(bm / rm) * (bn / cn)` work-items (a multiple of 32, at most the device limit) | 8, 16 / 4, 8 |
| `bk` | k per step; 32 halves the barriers per FMA | 16, 32 |
| `ku` | unroll of the loop over the k of a step (written out by the preprocessor, no `#pragma`) | 1, 2, 4, 8, 16 |
| `pf` | 0: load, convert, store, barrier, compute, barrier (like `mul_mm.cl`); 1: the global loads of the next step are issued before the compute of the current one (raw data in registers), converted and stored to the local memory after it; 2: as 1 with two local buffers (one barrier per step) | 0, 1, 2 |
| `ldg` | tile loads through `ld.global.nc` (inline PTX, NVIDIA sm_35+ only: needs the `use_nv_ldg` switch of the platform, `GGML_CL11_NO_LDG=1` turns it off) | 0, 1 |
| `reqd` | `reqd_work_group_size(NT, 1, 1)` | 0, 1 |
| `maxrreg` | `-cl-nv-maxrregcount` of the program that holds the mat-mat kernels (NVIDIA only; the mat-mat kernels are then built in a program of their own, like `GGML_CL11_SPLIT_PROGRAMS=1`) | 0 = none |

Why these parameters: the default kernel computes 8 x 4 values per work-item and needs 3 128-bit local memory loads per k for 32 FMAs; a Kepler work-item may use 255 registers (Fermi 63), so the
register tile can be larger (the ratio of local memory loads to FMAs is the thing a larger tile changes, see the table; whether it is what limits the kernel on a GK208 is the open question
of the sweep). `pf` and `bk` address the other cost, the time the staging of the tiles takes (35% of the time of the default kernel on the GT 430). The accumulators are scalars (`c<row>_<col>`) and every loop
that touches them is expanded by the preprocessor, so no compiler has to unroll anything to keep them in registers; the dst tile is written with float4 stores when dst is contiguous in m and
16-byte aligned. The dequantization is the one of the default kernel (a 16-byte unit of the repacked weights per row and 16-weight step, scale applied while the tile is written); for
`bk` = 32 a work-item handles two 16-weight steps, and the header of a Q4_K / Q6_K super-block is reloaded every 256 weights whatever the step. With `pf` > 0 the raw data of the next step (and the header)
is loaded while the current step is computed.

**Multi mat-vec `k_mvm_*`** (`src/backends/opencl11/kernels/mul_mv_multi.cl`; Q4_0 / Q8_0 in the base program, Q4_K / Q6_K in the K-quant program with its register cap). One launch computes up to 3 `MUL_MAT`s that read the same src1:
the Q / K / V projections of a layer and the FFN gate / up. The body of each kernel is the one of `k_mvr_<type>` (the macros of `mul_mv_r.cl` / `mul_mv_k.cl` are reused, nothing in them changed): a work-group first
takes the weight tensor (slot) its group index belongs to (slot 0: groups `0 .. tiles0 - 1`, slot 1 the next `tiles1`, slot 2 the rest), then its weight / dst pointers and descriptors, and runs the usual code with the group
index relative to the slot. The slots may have different numbers of rows (Qwen3-0.6B: Q 2048, K 1024, V 1024) and live in different `cl_mem` buffers (the weights of a model are split over several buffers); each slot is R32
repacked as before (the kernel reads it exactly like `k_mvr_*`). Conditions (`cl11_mvm_candidate`, `cl11_mvm_same_group`, `cl11_op_mul_mat_multi`):

- the MUL_MAT is a repacked weight matrix (Q4_0 / Q8_0 / Q4_K / Q6_K, a leaf of the graph, not a view) with ne2 = ne3 = 1, src1 F32 with a single column and no batch (decode), dst F32; `MV_MAX_COLS` >= 1;
- all the members have the same type of weights, the same row length (ne00) and the **same src1 tensor**; a different type (Qwen3-0.6B Q4_K_M: V is Q6_K in some layers) or shape is simply not part of the group (the others still are: a group of 2 of 3 is fused);
- not on a device where src1 goes through constant memory (`mvr_const_x`: the Fermi default), because that path has its own kernels; `GGML_CL11_MVR_CONST_X=0` allows it;
- at launch: 16-byte aligned offsets, and `CL_KERNEL_WORK_GROUP_SIZE` of `k_mvm_<type>` at least the work-group of the type (otherwise the nodes are computed one by one, no error).

The nodes of the Q, K and V projections are not adjacent in a llama.cpp graph (the reshape / RMS_NORM / MUL / RoPE of Q lie between them), so the backend implements `graph_optimize`
(called by `ggml_backend_sched` **before** the graph is allocated): for a candidate it looks 48 nodes ahead for candidates of the same group and moves them right behind it (order of the others kept). This is safe because a moved
node only reads a weight tensor and the src1 that the first node reads too, nothing between them reads its result, and the allocator sees the new order, so the lifetimes of the buffers are right. `graph_compute` computes
consecutive nodes of the same group with one launch (`GGML_CL11_PROFILE` shows `MUL_MAT <type> mv multi x<n> (fused)`). `tools/mvm_check.cpp` builds such graphs (with the nodes of Q / K between the projections, several
row counts including ones that are not a multiple of 32, weights in two buffers, mixed types) through `ggml_backend_sched` and compares the results with a double precision reference (`test-backend-ops` builds one `MUL_MAT` per graph, so it never fuses).

**Paired SET_ROWS `k_set_rows2_*`** (`get_set_rows.cl`): the writes of the K cache and the V cache of a layer (two `SET_ROWS` with only a view between them in the graph, same types, different destination tensors that the second
does not read) are one launch. Checked by `tools/mvm_check.cpp` (F16 / F32 caches, I64 / I32 row indices, different token counts) and by the greedy output.

#### Fermi round: "denormal products" mat-vec (GT 430; measured on the GPU 2026-10-09)

The mat-vec of the GT 430 (96 cores at 1.4 GHz, 22.9 GB/s) is close to instruction bound for the 4-bit types once src1 comes from constant memory (the hypothesis behind this change, to be confirmed by the measurement below). The normal kernels turn every
weight into a float with a `prmt` (a byte-permute that runs at 16 per clock and SM on Fermi, a fraction of the rate of the `FFMA` units; the bytes are the mantissa of `2^23 + b`), subtract the offset with an `FSUB` and then multiply-add: three instructions
per weight, one of them on the slow unit. The "denormal products" kernels (`mul_mv_r.cl`: `DN_Q4_WORD`, `MVR_Q4_DN_LOOP`; `mul_mv_k.cl`: `MVK_Q4_DN_LOOP`, `DNQ6_*`; `cfg.mvr_dn`, `DN_<TYPE>`) need one `AND` and one `FFMA`:

- **The trick.** A nibble (or byte) masked *in place* in a 32-bit word, `w & (0xF << p)`, read as a float is the exact value `n * 2^(p - 149)` for the bit positions `p` of the kernels (`p <= 20` for nibbles; bits 0..23 are
  a denormal or one of the smallest normal numbers, and the value is linear in `n` over that range). The `FFMA` of Fermi (the compiler does not set `.ftz` for OpenCL by default) multiplies denormals at full speed and exactly, so
  `fma(as_float(w & mask), xs, acc)` adds `n * x * 2^(DN_E - 149)` when `xs = x * 2^(DN_E - p)` (`DN_E = 100`, an exact power of two scale; the products are then about `2^-49 * n * x`, far from the denormal range of the accumulators).
  Byte 3 of a word (bits 24..31) is shifted down first. At the end of a block the accumulator is scaled back with `2^(149 - DN_E)` together with the block scale (`d`, or `d * sc` for the K-quants).
- **Offsets.** Q4_0 (`-8`), Q6_K (`-32`) and the `dmin` term of Q4_K are removed with the sums of x over groups of 16 weights (`sum * 2^(DN_E - 146)` etc.), not per weight.
- **`k_xprep` (`mul_mv_r.cl`).** One work-item per 16 weights of src1 writes the scaled column `xs` (K floats; low / high nibble and byte position select the factor `2^(DN_E - p)`, pattern parameter `hbit`: Q4_0 4, Q4_K 8,
  Q6_K 0) and then the K / 16 sums of the groups into a scratch buffer (`cfg`-independent, at most 64 KiB, one buffer per pattern). The mat-vec kernels read both from constant memory: the DN kernels *are* the `k_mvrc_*` kernels
  (compiled with `-DDN_Q4_0` etc.), the general `k_mvr_*` kernels (several columns, long vectors, batches) keep the normal arithmetic.
- **Reuse of the preparation.** `c->xprep[3]` remembers, for each pattern, which column (buffer, byte offset, size) the scratch buffer was made from. Q, K and V of a layer (and FFN gate and up) read the same src1: one `k_xprep` serves
  the three mat-vecs of the same pattern. The memory is invalid at the start of every `graph_compute` and whenever a node writes into an overlapping range (`cl11_xprep_note_write`, called for every node, for the extra nodes of the fused
  `ADD + RMS_NORM + MUL` / `RMS_NORM + MUL`, for the second `SET_ROWS` of a pair and for the members of a multi mat-vec group). Only a single column (`ne11 = ne12 = ne13 = 1`), `ne00 % 16 == 0` and
  `x + sums <= min(CL_DEVICE_MAX_CONSTANT_BUFFER_SIZE, 64 KiB)` take this path; anything else falls back to the normal constant-memory or global-memory kernels. Q8_0 has no DN kernel (`cfg.mvr_dn[Q8_0]` is forced to 0).
- **Probe (`cl11_dn_probe`).** The scheme is only valid where the multiply of a denormal is exact. Before the first program is built, a one work-item kernel computes `fma(as_float(w & mask), x * 2^100 ..., s)` for the bit positions 0, 8 and 20
  of a word and for a shifted byte and compares the sum with the exact value `(5 + 11 + 10 + 12) * 2^-49`. A device that flushes denormals (Apple GPUs, some Mesa drivers) fails it and gets the normal kernels with the message
  `does not multiply denormal floats exactly, the "denormal products" kernels are disabled`; on the Mac this is what `GGML_CL11_FORCE_GEN=fermi` shows. `GGML_CL11_DN_NOPROBE=1` skips the probe (for a device that is known to work).
  The probe is the only guard: **the DN kernels have never run on a device that executes them correctly**, the GT 430 is the first test.
- **Relation to the Kepler multi mat-vec (they exclude each other, `mvr_const_x` decides).** The DN kernels are the constant-memory kernels, so they run only where src1 goes through constant memory (`mvr_const_x`): the Fermi default.
  `cl11_mvm_candidate` refuses the multi mat-vec on such a device (and `graph_optimize` then does not move any node), so on Fermi: constant memory + DN, no `k_mvm_*`; on Kepler (`mvr_const_x` off, because the NVIDIA 390 driver ignores
  the offset of a sub-buffer passed as `__constant`): `k_mvm_*`, and DN has no kernel to run, so `cfg.mvr_dn` is cleared (with a message when it was asked for through the environment). Forcing both on one device:
  `GGML_CL11_MULTI_MV=1 GGML_CL11_MVR_DN=1` on a device with `mvr_const_x`: DN wins and the multi mat-vec is idle; `GGML_CL11_MVR_CONST_X=0 GGML_CL11_MULTI_MV=1` on Fermi: the multi mat-vec wins and DN is cleared;
  `GGML_CL11_FORCE_GEN=kepler GGML_CL11_MVR_DN=1`: DN is cleared, the multi mat-vec stays. (`test-backend-ops` and the graph checks pass with each of these on the Mac, see "Validation status"; the DN kernels themselves cannot run there.)
- **The paired `SET_ROWS` is independent of DN** (it does not read src1 of a mat-vec); with `GGML_CL11_FUSE_SET_ROWS=1` it works on Fermi too.

What is expected, and what is not known: fewer instructions per weight (3 -> 2, no `prmt`), so a higher mat-vec rate for Q4_0 / Q4_K / Q6_K on the GT 430 if the unit with the 16 per clock was the bottleneck, and a cost of one extra kernel
launch (`k_xprep`) per group of mat-vecs of one src1 plus the reading of the scratch column. **None of this has been measured**; the values below are filled in from `summary.md` of the sweep.

### Tried and not kept

- **Q4_0 without the per-weight subtraction** (the nibble in the mantissa of `2 + n/8` through `(w << 3) & 0x78787878`, correction
  `- 24 * sum(x)` of the block): 17.5 -> 18.9 G weights/s only (23.2 -> 24.4 with constant src1), and it needs the block sums of src1
  and costs 2 bits of precision: not kept. The same trick for Q8_0 needs the offset `2^15` (8-bit values do not fit under the exponent): ~10 bits lost, and Q8_0 is not instruction-bound anyway.
- **src1 in local memory for the mat-vec of the repacked weights** (staged per warp, one barrier per 4 blocks): the same speed as the
  global loads (16.5 GB/s): the local loads are load / store instructions too. Constant memory is the one that helps.
- **More rows per lane / other work-group sizes** (`GGML_CL11_MVR_NRR`, `GGML_CL11_WG_MVR`; tg of Qwen3-0.6B Q8_0 / Qwen2-0.5B-ft Q4_0, t/s):
  NRR=1: 19.7 / 29.5 (128 items), 19.2 / 25.7 (64); NRR=2: 20.4 / 28.6 (128), 21.2 / 29.0 (64), 18.3 / 25.2 (256), 15.1 / 19.5 (32);
  NRR=3: 15.7 / 24.1; NRR=4: 15.4 / 20.6 (64). Registers (63 on Fermi) and the number of warps are the limit. 64 items x 2 rows is the default.
- **Software prefetch / hoisting of the loads of the next block** (explicit double buffering in registers): no change (13.3 vs 13.7 G weights/s):
  the occupancy already covers the latency; the x loads were the limit.
- **Unrolling the loop of `k_mv_f16` / `k_mv_f32`** (4 chunks loaded together, kept: attention K mat-vec 137 -> 125 us) and of `k_mvt_f16`
  (8 independent loads: 113 -> 154 us, reverted).
- **`GGML_CL11_MVS_MIN_K=64`** (the x kernels for the K cache): 137 -> 195 us. `GGML_CL11_WG_MV` 64 / 256: no gain for the attention kernels.
- **Mat-mat tile 64 x 64** (`GGML_CL11_MM_BN=4`, 128 work-items): +2-6% for Q8_0 / Q4_0 (99.7 GFLOPS), but -10..-20% for the other types on the GT 430;
  64 x 128 is the default there (64 x 64 is faster on Kepler, see above).
- **Constant memory for src1 on Kepler** (`k_mvrc_*`): wrong results (the 390 driver ignores the offset of a sub-buffer used as `__constant`, it reads the
  base of the parent buffer: found by `test-backend-ops` and the greedy output; a micro test shows that the sum of the constant array is the sum of the
  start of the parent buffer for every offset except 0). The sweeps that were made with it were discarded. On Fermi it works and stays on.
- **Denormal trick / other conversions for the nibbles** (the nibble masked in place as the mantissa of a denormal float, products with a pre-scaled src1):
  the low nibbles fit under bit 23 only for 5 of the 8 positions and src1 would have to be scaled by `2^120`; the instruction count of the conversion is
  not the only limit of the K-quants on the GT 730 (removing the conversion and the sums altogether gives 65%, removing the loads of src1 as well 88%).
- **`ld.global.nc` for the weights** (Q4_K): 43% instead of 61% of the streaming rate.
- **Lanes per row for the K cache with the loop over the positions in each lane** (1-16 lanes per row of 256 bytes of one head, 16 lanes -> 385 us, 1 lane -> 153 us):
  slower than the version that reads the whole 2 KiB rows of all the heads (92 us).
- **Software prefetch / more loads in flight** in the attention kernels and `GGML_CL11_ATT_P` / `GGML_CL11_WG_ATT` (see "Attention kernels").
- **Several command queues** (independent kernels in different queues): the GPU needs ~12 us per kernel (GT 710) whatever the queue, the fixed cost is not
  hidden by overlapping.
- **Q4_K / Q6_K with `GGML_CL11_MVR_NRR` 1 / 3 / 4 and `-cl-nv-maxrregcount` 64..255**: NRR=2 is the best on both Kepler GPUs (Q4_K, GT 730: NRR=1 44%, 2 69%,
  3 62%; Q6_K: 62% / 75% / 44%), the cap helps only between 112 and 128 registers (the speed is not monotonic in the cap: 160 and 255 are *slower* than 128).
- **Repacking with 8 bytes of src1 per lane, unrolling the loop over the units, staging the rows in local memory, occupancy
  (`-cl-nv-maxrregcount`)** for the natural layout (earlier round): no gain.

### Per-GPU tuning

Everything that depends on the GPU is chosen in one place, `cl11_tuning_for()` (`src/backends/opencl11/device.cpp`), from the compute capability
(`cl_nv_device_attribute_query`, stored in `cl11_device_info::nv_cc_major / nv_cc_minor`), the AMD generation (`cl11_amd_generation()`, see below),
the number of compute units (`CL_DEVICE_MAX_COMPUTE_UNITS`) or the device name. The Fermi (compute capability 2.x / "GT 430"), the Kepler
(compute capability 3.x / "GT 730", "GT 710") and the AMD GCN ("Radeon Pro WX 2100") branches have values measured on the real GPU. Every AMD GPU gets the settings that

(measured on the WX 2100 only), so an AMD GPU of the RDNA generation (RX 6400) or of an unknown generation does not get them. Mesa Clover (any GPU) additionally gets `split_programs`.
Every other device gets the defaults until it is measured.

2. a `gfxNNN` token in the device name (ROCm names the device after its ISA: `gfx803`, `gfx90a` are GCN, `gfx1034`, `gfx10-3-generic` RDNA);
3. the code name that Mesa puts into the device name (rusticl and Clover alike; the tokens of the last parentheses):

4. the marketing name: `Pro WX` and `RX nnn` (3 digits, RX 4xx / 5xx = Polaris) are GCN, `RX nnnn` (4 digits) RDNA.

(`CL_DEVICE_MAX_CONSTANT_BUFFER_SIZE`, queried) are compile-time / device-queried; the quantized layouts are not tunable.

### AMD Radeon Pro WX 2100 (Polaris 12, Mesa Clover / rusticl)

Radeon Pro WX 2100: GCN4, 8 CUs (512 shaders, wave64), 2 GiB GDDR5 on a 64-bit bus, PCIe x1, `CL_DEVICE_MAX_MEM_ALLOC_SIZE` 512 MiB,
measured with a float4 streaming kernel: 43.5 - 43.7 GB/s read (peak 48), 33 GB/s write, 0.1 - 0.4 GB/s host to device (a model takes a few
seconds to load). Power (amdgpu hwmon `power1_input`): 3.2 W idle, about 21 W while Vulkan decodes, 13 - 17 W while CL11 decodes.
Both Mesa implementations expose the card: Clover (OpenCL 1.1; `unset RUSTICL_ENABLE`) and rusticl (OpenCL 3.0; `RUSTICL_ENABLE=radeonsi`, then
rusticl is `CL11_0` and Clover `CL11_1`); use `GGML_CL11_DEVICES="WX 2100"`. The kernels need no change for wave64: every cooperation
inside of a work-group goes through `barrier()`, `lane = lid & 31` is a row of a group of 32 rows, not a hardware lane.

What was found (all numbers: Qwen3-0.6B Q8_0 unless noted, `-ub 128 -b 128`):

- **rusticl emulates `fma()` in software on GCN.** A micro benchmark with independent chains: `fma` 14.3 us per iteration and work-item,
  `mad` / `a * b + c` 0.118 us (120x); on Clover `fma` is native but 1.8x slower than `mad`. Every mat-mat FMA was a library call: the tiled kernel
  ran at 3.5 GFLOPS, `llama-bench` pp128 3.77 t/s. The kernels use `CL11_FMA(a, b, c)` (`mad` on AMD, `fma` everywhere else, `-DCL11_MAD`):
  mat-mat 3.5 -> 450 GFLOPS (Q8_0, 64 x 128 tile), rusticl pp128 3.77 -> 446 t/s. (`mad` is not fused, the results differ from the CPU in the last bit;
  the greedy outputs below are unchanged.) Unrolling the loops (`#pragma unroll`) and keeping the 32 accumulators in `float4` variables
  made no difference: they were already in registers.
- **Tile 64 x 64** (`mm_bn = 4`, 128 work-items) instead of 64 x 128: 345 -> 530 GFLOPS (rusticl, m=4096, n=512, k=4096, Q8_0), 428 -> 456 (Clover); Q4_0 is
  the same or better. 32 x 32 work-groups (`gt = 32`, up to 626 GFLOPS on rusticl) are not accepted by Clover (maximum work-group size 256).
- **Mat-vec of the repacked weights**: a 3072-row matrix has only 48 work-groups of 64 work-items with 2 rows per lane (8 CUs). 256 work-items and 1 row per lane
  (96 groups, 8 warps split the blocks) read 35 GB/s instead of 21 GB/s for a 3072 x 1024 Q8_0 matrix (isolated kernel, clocks at their maximum), 41.9 GB/s instead of
  37 GB/s for the output matrix (151936 rows) and 41.5 instead of 39 GB/s for m=4096, k=14336. Decode on Clover (Qwen3-0.6B Q8_0 / Qwen2-0.5B-ft Q4_0): 64 x 2: 18.0 / 21.2 t/s, 64 x 1: 19.5 / 23.0,
  128 x 1: 19.7 / 25.4, 256 x 1: 20.2 / 25.6.
- **Decode is limited by the dispatches, not by the mat-vec.** Back-to-back launches of an empty kernel cost about 90 - 120 us each on rusticl and 15 - 20 us on Clover
  (the GPU is idle between the dispatches), and a token of Qwen3-0.6B is about 750 dispatches (the ~500 elementwise / norm / rope / copy kernels run for
  9 - 25 us each): rusticl 13.5 t/s, Clover 20 t/s, whatever the mat-vec does (Clover: 35 ms of kernel time and 15 ms of gaps per token, the
  weights are read at 27 GB/s on average; `time`: user + sys is 75% of the wall time). The only remaining lever is fewer kernels: fusing `RMS_NORM` + `MUL`
  (4 per layer) would save 112 of ~750, about 3% of a token; not done.
- **The launch cost on Clover grows with the size of the program.** A micro benchmark (empty kernel, in-order queue, 1 work-item) costs 5 / 24 / 104 us per `clEnqueueNDRangeKernel` when the program that holds
  the kernel also holds 0 / 50 / 200 other kernels; rusticl does not depend on the size. With all the kernels of CL11 in one program, every one of the ~750 launches of a token paid for the size of the whole program.
  `split_programs` (on with Clover, `GGML_CL11_SPLIT_PROGRAMS=0/1`) builds three programs: the decode kernels, the mat-mat kernels (`-DCL11_ONLY_MM`) and the K-quant kernels (`-DCL11_PROG_K`), which are built when the first
  K-quant weight is used. Qwen3-0.6B Q8_0 on Clover: tg64 16.15 -> 22.66 t/s, pp128 320 -> 345 t/s (same build, only the environment variable differs).
- **The single work-group V cache kernel is 8x slower with a work-group of 256.** `k_mvt_f16` (the transposed F16 V cache fused with the `CONT`, `attn.cl`) computes a batch in ONE work-group and was written
  for 1024 work-items (512 on Fermi). Mesa allows 256: 307 us per call instead of 38 us for `k_mvt_g_f16` (many work-groups, tiles of 32 outputs), tg64 of Qwen3-0.6B Q8_0 on Clover 13.9 -> 20.1 t/s (before
  `split_programs`). `cfg.mvt_groups` selects the second kernel (AMD, or whenever `wg_att` < 512).
- **Memory clock.** With the CL11 decode the amdgpu memory clock flaps between 300, 625 and 1500 MHz (the load is latency bound with idle gaps), the Vulkan decode holds
  1500 MHz at 100% busy (a micro benchmark that runs a kernel for a second holds 1500 MHz too). On rusticl the `GGML_CL11_PROFILE` times include its
  dispatch latency (a 3072 x 1024 Q8_0 mat-vec: 318 us in the model, 95 us in a loop; on Clover the two agree). The clocks can only be forced as root
  (`power_dpm_force_performance_level`), not tried.
- **K-quants** (Q4_K / Q6_K mat-vec of the repacked weights, `k_mvr_*` of `mul_mv_k.cl`) read only 11 GB/s (Q4_K) and 17 GB/s (Q6_K) on Clover (`GGML_CL11_PROFILE`, Qwen3-0.6B Q4_K_M): they are
  instruction bound and were written for 32-wide warps. The work-group size and the rows per lane decide how much of the latency is hidden (tg64 of Qwen3-0.6B Q4_K_M, Clover, both types set together,
  default = 64 x 2): 64 x 1 17.95, 64 x 2 16.40, 128 x 1 **19.62**, 128 x 2 17.23, 256 x 1 18.16, 256 x 2 15.16 t/s; Q4_K 128 x 1 with Q6_K 64 x 1 / 256 x 1: 19.31 / 18.89 t/s. rusticl (WX 2100): default 14.72, 128 x 1 **16.24**,
  64 x 1 15.61, 256 x 1 15.79 t/s. The same 128 x 1 is the best or tied on the RX 6400 (rusticl, tg128: default 20.5 / 21.0, 64 x 1 23.7 / 22.4, 128 x 1 24.9 / 23.6 t/s, run-to-run spread 1-4 t/s), so it is set for every AMD GPU.

## Allocations larger than the nominal limit

`alloc_buffer` does not refuse sizes above `CL_DEVICE_MAX_MEM_ALLOC_SIZE`: it tries `clCreateBuffer` (the NVIDIA
390 driver accepts them and they work). The limit of such an allocation is `CL_DEVICE_GLOBAL_MEM_SIZE`, and 2 GiB
(`0x7ffff000`) in any case, because the kernels address a buffer with 32-bit signed byte offsets (and the
tensor descriptors, element counts and `group * work-group size` products are 32-bit as well; `supports_op` rejects
tensors that would overflow them). Since some drivers allocate lazily, an allocation above the nominal limit is
followed by a blocking write to the last bytes of the buffer, and the buffer is released (`alloc_buffer` returns
`nullptr`) if that fails. The first such allocation logs a warning.

`GGML_CL11_STRICT_ALLOC=1` restores the strict behavior: allocations above `CL_DEVICE_MAX_MEM_ALLOC_SIZE` are refused.
The AMD branch of `cl11_tuning_for` sets it (Mesa Clover / rusticl answer `CL_INVALID_BUFFER_SIZE`), and `supports_op` returns false for an op with a tensor
above the limit (512 MiB on the WX 2100), so such a tensor is computed by the CPU backend instead of failing to allocate.

## Validation status

Done on a real GeForce GT 430 (Fermi, NVIDIA 390.157, OpenCL 1.1 CUDA), by the maintainer:

- Before the "allocations larger than the nominal limit" change: `test-backend-ops -b CL11_0` passed 1981/1985
  cases. The 4 failures were all one tensor larger than `CL_DEVICE_MAX_MEM_ALLOC_SIZE` (241 MiB) rejected by
  `alloc_buffer` (`GET_ROWS` with be1=700, be2=100 in F32 and Q4_0, `MUL_MAT_HADAMARD` 8192^2 and 16384^2).
  The NVIDIA 390 driver was checked to accept `clCreateBuffer` larger than the nominal limit (300 MiB, 400 MiB)
  with correct writes / reads at the end of the buffer.
- After the change: 1984/1985 passed. The remaining case is `MUL_MAT_HADAMARD` F32 16384^2, a tensor over
  1 GiB, larger than the 964 MiB of VRAM (expected).
- Qwen3-0.6B Q8_0, `-ngl 99`: the greedy output (64 tokens) is identical to the CPU backend with `-ub 128`.
  With the default `-ub 512` the compute buffer is too large: the logits are one `n_ubatch x n_vocab x 4 bytes`
  tensor (512 x 151936 x 4 = 297 MiB), and 604 MiB of weights + KV cache + this buffer exceed the VRAM, so the
  allocation fails with `CL_MEM_OBJECT_ALLOCATION_FAILURE` and llama.cpp stops with an error.
