# AMD GPU の Vulkan（ggml-vulkan）をどこまで詰められるか

状態: 調査済み（2026-10-08）。WX 2100（Polaris 12 / GCN）と RX 6400（RDNA2 / navi24）で、llama.cpp b11384 の公式 Vulkan ビルド（ggml-vulkan、Mesa 25.0 の RADV）が、ハードの帯域と演算の上限にどこまで近いか、残りをどこで詰められるかを実測で調べました。実装はしていません。

- 計測は TB250（Celeron G3930、2 スレッド）。特に断らない限り `-ngl 99`、`GGML_VK_VISIBLE_DEVICES` で 1 枚だけ見せた単独計測、`llama-bench -p 128 -n 64`（tg64、本書では tg(A)）または `-p 0 -n 256 -r 3`（tg256、電力用）です。GPU は 1 台ずつ、ほかの計測と重ならないようロックして測りました。
- 電力は amdgpu の hwmon（RX 6400 は `power1_average`、WX 2100 は `power1_input`）を 0.1 秒間隔で記録し、負荷中の平均を取りました。分解能は 1 W 程度なので、J/token は ±5% 程度の目安です。
- スクリプトとログは TB250 の `~/bench/scrapgpu/_w/vk/`（`notes.md` に経過）にあります。
- リンクは RX 6400 が Gen2 x4（理論約 2 GB/s）、WX 2100 は Gen2 x1（約 0.5 GB/s）です（[HARDWARE.md](HARDWARE.md)）。OpenCL（rusticl）で測った転送は、RX 6400 でホスト→GPU 1.42 GB/s・GPU→ホスト 1.0〜1.26 GB/s、WX 2100 で 0.36 / 0.29 GB/s、4 バイトの往復レイテンシは約 0.1〜0.16 ms でした。

## 結論

| | RX 6400 | WX 2100 |
| --- | --- | --- |
| 実効帯域（OpenCL の読み出しカーネル） | 126.6 GB/s | 43.6 GB/s |
| 1 本の tg: Qwen3-0.6B Q8_0 の上限 / 現状 | 200 / 140 t/s（70%） | 69 / 46.5 t/s（68%） |
| 1 本の tg: 上限比の範囲（6 モデル） | 55〜77% | 49〜73% |
| 1 本の tg: 詰められる見込み | `-bs` +4〜12%、形式の選択（Q8_0 → Q4_K_M で +28%）、小さい op の融合で +10〜15%（推定）。0.6B Q4_K_M なら現状の 129 t/s（サンプリング込み）から 178 t/s まで、実測で到達済み | `-bs` +5〜10%、形式の選択（Q8_0 → Q4_K_M で +30%）。小さい op に 3.8 ms/token かかっており、融合の余地は RX 6400 より大きい |

| 合計スループット: ハードの上限 | プロンプト処理の速度 約 2600 t/s（演算律速） | 約 550 t/s |
| 電力 | 小さい Q4 系で 0.16〜0.18 J/token（B=1）。バッチでは 0.05 J/token 以下 | 0.39〜0.54 J/token（B=1）。バッチでは 0.12 J/token 以下 |

- tg の上限比が 5〜7 割にとどまる主因は、重みの量に比例しない固定費（RX 6400 で 1 トークンあたり約 2〜2.6 ms、WX 2100 で 5〜8 ms）です。小さいモデルほど割合が大きくなります。8B クラスは固定費が約 7.6 ms で、K-quant（特に Q3_K）の mat-vec の帯域効率が足りない分が目立ちます。
- 合計スループットはバッチ処理（同時シーケンス）で伸びます。B=4 まではほぼ線形で、B=8 以降は伸びが鈍り、演算律速（プロンプト処理の速度）の 3 割程度で止まります。
- **GPU 側のサンプリング `-bs`（`--backend-sampling`）は b11384 にあり、Vulkan で動きます。** 実測で +4〜12% です。実装は不要です。
- 2 枚の協調は、1 枚に載らないモデルを `-sm layer` で動かすことに使えます。8B-ft Q4_K_M は `-ts 8/1` で 14.1 t/s でした。速度のために 2 枚を使う手段（`-sm row`、`-sm tensor`、WX 2100 をドラフトにした投機的デコード）は、どれも 1 枚より遅くなりました。

## 2. 1 トークンの内訳

`GGML_VK_PERF_LOGGER=1`（ggml-vulkan.cpp が読む環境変数。ほかに `GGML_VK_PERF_LOGGER_FREQUENCY`、`GGML_VK_PERF_LOGGER_CONCURRENT`、`GGML_VK_SYNC_LOGGER`）で op ごとの GPU 時間を取り、`perfparse.py` でデコード 127 グラフを集計しました。

**注意: ロガーは小さい op の時間を実際より大きく見せます。** 0.6B Q4_K_M や Qwen2-0.5B-ft では、GPU 時間の合計がロガー無しの壁時計を上回りました（10.1 ms 対 5.65 ms）。信頼できるのは、GPU が飽和している場合（8B Q2_K。ロガー有りの GPU 合計 31.4 ms に対し、ロガー無しの壁時計 32.0 ms）と、0.6B Q8_0 の RX 6400（合計 6.82 ms に対し壁時計 7.25 ms）、WX 2100（20.3 ms に対し 22.0 ms）の 3 件だけです。ほかは割合の目安にとどめます。

| 区分 | RX 6400 0.6B Q8_0 | WX 2100 0.6B Q8_0 | RX 6400 8B Q2_K |
| --- | --- | --- | --- |
| mat-vec | 5.72 ms（79%）、重み 633 MB ÷ 5.72 ms = 111 GB/s（実効帯域の 88%） | 16.56 ms（75%）、38.3 GB/s（88%） | 29.27 ms（91%）、重み 3011 MB ÷ 29.27 ms = 103 GB/s（81%） |
| norm（RMS_NORM_MUL と QK-norm + rope + set_rows の融合） | 0.53 ms（7%） | 1.69 ms（8%） | 1.12 ms |
| attention（FLASH_ATTN_EXT、コンテキスト 256） | 0.39 ms（5%） | 1.45 ms（7%） | 0.75 ms |
| その他（SET_ROWS、GLU、ADD、GET_ROWS） | 0.17 ms（3%） | 0.65 ms（3%） | 0.25 ms |
| GPU の op 合計 | 6.82 ms（94%） | 20.35 ms（92%） | 31.39 ms |
| ホスト側（壁時計 − GPU 合計。submit、フェンス待ち、logits の読み戻し） | 約 0.43 ms | 約 1.65 ms | 約 0.6 ms |
| 壁時計（ロガー無し） | 7.25 ms | 22.0 ms | 32.0 ms |

- 1 トークンの dispatch は約 397 回（mat-vec 197、その他 200）。小さい op は 1 回 3〜11 µs（RX 6400）で、融合しても減らせる分は限られます。
- 上限（RX 6400 の 0.6B Q8_0 で重みだけ 5.00 ms）との差 2.25 ms は、mat-vec の帯域効率 0.7 ms、小さい op 1.1 ms、ホスト側 0.43 ms に分かれます。
- **8B Q2_K の mat-vec は、形式によって効率が違います**（`perf` の op 時間と各形式のブロックサイズから計算）。

  | op | 帯域 |
  | --- | --- |
  | Q2_K（gate / up、m=12288、k=4096） | 121 GB/s |
  | Q2_K（q 射影、m=4096） | 111 GB/s |
  | Q6_K（出力、m=151936） | 126 GB/s |
  | **Q3_K（ffn down、m=4096、k=12288）** | **86 GB/s** |
  | **Q3_K（attn output、m=4096、k=4096）** | **80 GB/s** |

  Q3_K の 1030 MB を 120 GB/s で読めれば 3.7 ms/token（11%）速くなります。Q2_K と Q3_K が混ざる Q2_K モデルで目立つ弱点です（要検証。upstream の候補）。
- 0.6B Q8_0 の mat-vec の個別の効率: gate / up（m=3072）112 GB/s、qkv（m=2048）107 GB/s、o（m=1024、k=1024）101 GB/s、down（m=1024、k=3072、ADD 融合）104 GB/s。小さい行列ほど立ち上がりの影響が見えます。

### logits の読み戻しとサンプリング

n_vocab=151936 なので、logits は 607,744 バイトです。`-bs` の有無で比べた eval time（デコード時間）の差が、読み戻し（と GPU 側 argmax / top-k の追加分の差）です。

| | eval の短縮（読み戻し分） | CPU のサンプラー |
| --- | --- | --- |
| RX 6400（0.6B Q8_0 / Q4_K_M / 1.7B / 8B） | 0.05 / 0.06 / 0.01 / 0.18 ms（0.1〜1%） | 0.43〜0.50 / 0.50 / 0.58〜0.61 / 1.05〜1.09 ms |
| WX 2100（0.6B Q8_0 / 1.7B） | 1.2〜1.35 / 1.05 ms（5〜6%） | 0.64〜0.87 / 0.94〜1.0 ms |

RX 6400（Gen2 x4）は読み戻しがほぼ無視できます。WX 2100（Gen2 x1）は読み戻しに 1〜1.35 ms/token かかります（OpenCL で測った 607,744 バイトの転送 2.7〜2.9 ms より小さく、ggml-vulkan が固定（pinned）ホストメモリへ非同期に転送するためと思われます）。

## 3. 手段の評価

### a. GPU 側のサンプリング（`-bs`）

b11384 にあります。`--help` の `-bs, --backend-sampling`（experimental、既定は無効。環境変数 `LLAMA_ARG_BACKEND_SAMPLING`）で、`llama-completion`、`llama-server`、`llama-batched-bench` などの共通引数です。実装は `src/llama-sampler.cpp` の `backend_apply` で、greedy は `ggml_argmax`、top-k は `ggml_top_k`、top-p、min-p、temp、dist（softmax + cumsum + 乱数との比較）、penalties が GPU のグラフに入ります。ggml-vulkan は `ARGMAX`、`TOP_K`、`ARGSORT`、`SOFT_MAX` を持っています。制約は、grammar や reasoning budget と併用できないこと、`-sm tensor` では CPU に戻ること、`backend_apply` を持たないサンプラー（dry、xtc、typical、mirostat など）を含む構成では使えないことです。

計測は `llama-completion -n 192 -c 512 --temp 0 -s 1 --ignore-eos`（eval + CPU のサンプリングの ms/token から求めた t/s）。「既定」は top-k 40 などの既定のサンプラー列、「greedy」は top-k 1 のみです。

| GPU / モデル | 既定 | 既定 + `-bs` | 効果 | greedy | greedy + `-bs` | 効果 |
| --- | --- | --- | --- | --- | --- | --- |
| RX 6400 / 0.6B Q8_0 | 129.2 | 138.7 | +7.3% | 129.9 | 140.0 | +7.8% |
| RX 6400 / 0.6B Q4_K_M | 162.6 | 178.5 | +9.8% | 162.9 | 182.1 | +11.8% |
| RX 6400 / 1.7B Q4_K_M | 83.0 | 87.2 | +5.1% | 82.6 | 87.5 | +5.9% |
| RX 6400 / 8B Q2_K | 30.1 | 31.2 | +3.7% | 30.2 | 31.4 | +4.0% |
| WX 2100 / 0.6B Q8_0 | 43.7 | 48.1 | +10.1% | 44.4 | 48.7 | +9.7% |
| WX 2100 / 1.7B Q4_K_M | 26.2 | 27.6 | +5.4% | 26.1 | 27.8 | +6.5% |

- 効果の大半は、152k 語彙に対する CPU のサンプラー（Celeron で 0.45〜1.1 ms）を消すことです。RX 6400 では読み戻しそのものはほぼ効きません。WX 2100 では読み戻しも 1 ms 以上減ります。
- `llama-bench` の tg は CPU のサンプリングを含まない（logits は読み戻す）ので、`-bs` の効果はベンチの数値に出ません。llama-server など実際のアプリの tg は、ベンチより 4〜12% 低くなっているはずです。
- ScrapGpuLibrary 側で独自にサンプリングを GPU に載せる場合の上限は、上の効果（RX 6400 で最大 0.5 ms/token、WX 2100 で最大 2 ms/token）です。llama.cpp 側に既にあるので、作る理由はありません。

### b. 量子化形式

Qwen3-0.6B-Base の F16（TB250 の `/mnt/hdd/specbench-models/qwen3-0.6b-base-f16.gguf`）から `llama-quantize` で各形式を作りました（`~/bench/scrapgpu/_w/models/q06b-*.gguf`）。Qwen3-1.7B の F16 / BF16 は TB250 に無く、8B の F16 はあるものの CPU 基準の KLD に数時間かかるため測っていません。IQ3_XXS は imatrix が必要で、imatrix は作らない方針のため省きました。

KLD は、CPU（b11384、`-dev none -ngl 0`）の F16 の logits を基準にし、RX 6400 の Vulkan で測っています（`llama-perplexity -c 512 --chunks 8 -b 128 -ub 128 -t 2`、CL11.md の Validation status と同じ文章 4096 トークン、F16 の PPL は 12.663）。tg は `-p 0 -n 256 -r 3`。「重み」は GGUF のファイルサイズです（1 トークンで読む量は 6 MB ほど少ない）。

- **帯域律速の予想（バイト数が少ないほど速い）は、Q4 付近までしか当たりません。** Q4_0 / IQ4_NL（約 383 MB）で RX 6400 は 184 t/s に頭打ちで、Q3 以下は 162〜176 t/s と、むしろ遅くなります。固定費が約 2.4 ms あるうえ、K-quant / IQ の mat-vec は Q4_0 より帯域効率が低いためです。
- **Q8_0 → Q6_K で +17%（KLD は +0.006）、→ Q4_K_M で +28%（KLD 0.065）、→ Q4_0 で +32%（KLD 0.129）。** 0.6B のような小さいモデルでは Q4 の品質低下が大きく（PPL が +7〜15%）、Q3 以下は壊れます（IQ3_S と Q2_K は PPL 43〜44）。
- 速度と品質の両方を見ると、有力な選択は Q6_K か Q5_K_M（Q4_K_M より 5〜9% 遅いだけで、KLD は 1/3〜1/8）、速度優先なら Q4_K_M です。Q4_0 と IQ4_NL は Q4_K_M より 3% 速いだけで KLD が 1.4〜2 倍なので勧めません。
- J/token は帯域律速の範囲では tg に反比例します。WX 2100 は RX 6400 の約 2.5 倍です。
- 8B や 1.7B の形式別の KLD は未測定です（F16 の基準がない、または時間がかかるため）。

### c. バッチ処理のスループット

`llama-batched-bench -c 4096 -b 2048 -ub 512 -npp 16 -ntg 64`。npl のリストを 2 回続け、2 回目の値を使います（1 回目は初回のパイプライン生成で B=8、16 が落ちる）。表は S_TG（tg の合計 t/s）。

| GPU / モデル | B=1 | 2 | 4 | 8 | 16 | 32 |
| --- | --- | --- | --- | --- | --- | --- |
| RX 6400 / 0.6B Q8_0 | 133.9 | 229.1 | 402.5 | 506.0 | 478.8 | 757.5 |
| RX 6400 / 0.6B Q4_K_M | 166.5 | 287.0 | 393.5 | 507.0 | 557.5 | 842.8 |
| RX 6400 / 1.7B Q4_K_M | 85.6 | 156.9 | 226.9 | 277.6 | 292.1 | 485.8 |
| RX 6400 / 8B Q2_K | 31.0 | 51.9 | 71.7 | 87.5 | 66.1 | |
| WX 2100 / 0.6B Q8_0 | 44.6 | 73.4 | 99.2 | 117.5 | 145.2 | 208.6 |
| WX 2100 / 0.6B Q4_K_M | 56.0 | 84.3 | 105.3 | 96.6 | 130.3 | 192.8 |
| WX 2100 / 1.7B Q4_K_M（`-c 1024 -ub 128`） | 26.4 | 43.1 | 56.1 | 52.0 | 58.2 | |

- **B=4 まではほぼ線形**です（RX 6400 の 0.6B Q8_0 で B=4 は 3.0 倍）。1 回の重みの読み込みで 4 トークン進みます。
- **谷があります。** RX 6400 は B=16（B=8 より遅いか同等）、WX 2100 は B=8（Q4_K_M、1.7B）が谷です。ggml-vulkan は N ≤ 8 を mat-vec 経路（`mul_mat_vec_max_cols = 8`）、それ以上を mat-mat 経路で処理するため、経路の切り替えの前後で効率が変わります。RX 6400 は B ≤ 8 または B ≥ 32、WX 2100 は B=4 または B ≥ 16 を使うのが無難です。
- **コンテキスト長（`-c`）を実際に必要な分に絞ります。** 0.6B Q8_0 の B=32 で、`-c 4096` なら 757 t/s、`-c 10240` なら 548〜598 t/s（`-kvu`）と 501 t/s（`-no-kvu`）でした。attention が確保した KV の長さに比例するためです。B=64 / 128（`-c 10240`）で 603 / 642 t/s と伸びが止まるのも同じ理由と思われます。0.6B Q4_K_M を `-c 10240` で測ると B=8 で 189 t/s と大きく落ちた原因は未調査です（`-c 4096` では 507 t/s）。
- **演算律速との比較**: RX 6400 のプロンプト処理（mat-mat）は 2400〜2700 t/s で、0.6B（約 1.2 GFLOP/token）なら約 3 TFLOP/s と FP32 のピーク近くです。tg の合計は B=32 でその 29〜32%（757〜843 / 2600）で、残りは attention と小さい op のオーバーヘッドです。WX 2100 は mat-mat が約 550 t/s で、tg の合計は B=32 で 38% です。
- **電力**: 負荷中の電力は B によらずほぼ一定（RX 6400 で 26〜33 W、WX 2100 で 24〜25 W）なので、J/token は B に反比例して下がります。B=32 の上限見積もりは、RX 6400 の 0.6B Q4_K_M で 30 W ÷ 843 t/s ≒ 0.036 J/token、WX 2100 の 0.6B Q8_0 で 25 W ÷ 209 t/s ≒ 0.12 J/token で、B=1 の 1/5 前後です。
- **用途への示唆（tb250-distill の Teacher など）**: 候補ごとの採点（固定の文章の logprob を求める）は、トークンごとに生成するのではなく、全トークンを 1 回のデコードで流すプロンプト処理の形にできます。その速度が約 2400〜2700 t/s（RX 6400、0.6B）で、tg の 1 本（140 t/s）の約 18 倍、B=32 の tg の 3 倍以上です。

### e. 2 枚の協調

`llama-bench`（`-dev Vulkan0/Vulkan1`、複数デバイスの区切りは `/`。`,` は別々の計測になる）。pp128 / tg64（t/s）。

| モデル | 構成 | pp128 | tg64 |
| --- | --- | --- | --- |
| 8B-ft Q4_K_M（4.7 GB） | RX 6400 のみ（4 GB を超えた分はシステムメモリ） | 55.2 | 3.2 |
| | 2 枚、`-sm layer`（既定の分割） | 95.9 | 10.75 |
| | `-sm layer -ts 5/2` / `3/1` / `7/3` / `4/1` | 107.6 / 115.2 / 100.5 / 134.5 | 11.70 / 12.03 / 11.40 / 12.76 |
| | `-sm layer -ts 6/1` / `8/1` | 164.8 / 185.5 | 13.64 / **14.06** |
| | `-sm row` | モデルの読み込みでエラー | `device Vulkan0 does not support split buffers` |
| | `-sm tensor`（50:50） | 10.4 | 0.303（WX 2100 の担当 2.5 GB が 2 GB の VRAM を超えて溢れた） |
| 8B Q3_K_S（3.5 GB） | RX 6400 のみ | 248.6 | **23.8** |
| | 2 枚、`-sm layer`（既定）/ `-ts 3/1` | 88.5 / 108.9 | 10.66 / 11.16 |
| | `-sm tensor`（50:50）/ `-ts 3/1` | 40.9 / 60.4 | 8.66 / 11.26 |
| 0.6B Q8_0 | RX 6400 のみ | 2437 | 140.1 |
| | 2 枚、`-sm layer` | 1099 | 54.1 |
| | `-sm tensor` | 325 | 29.9 |
| | `-sm row` | エラー（同上） | |
| 参考（specbench）: 8B Q2_K の `-sm layer` | | | 12.64（RX 6400 のみで 29.7） |

- **`-sm layer` は、1 枚に載らないモデルを動かす手段として有効**です（3.2 → 14.1 t/s）。RX 6400 に載る限り多く持たせるほど速くなります（`-ts 8/1` が最良。それ以上は RX 6400 の 4 GB に入らない）。1 本のストリームでは層が直列に実行されるため、2 枚の帯域は足されず、1 枚に載るモデルは分割で遅くなります（8B Q3_K_S は 23.8 → 11）。
- **`-sm row` は Vulkan で使えません。** ggml-vulkan にスプリットバッファ型が実装されていないためです（`llama-model.cpp` が `ggml_backend_split_buffer_type` を要求）。
- **`-sm tensor`（テンソル分割）は動きますが、PCIe では実用にならない**と判断します。0.6B Q8_0 で、載っているのに 1 トークンが 7.2 ms から 33 ms に伸びました。増えた約 26 ms を 28 層 × 2 回の allreduce（`ggml-backend-meta.cpp`）で割ると 1 回約 0.46 ms で、通信量（n_embd × 4 B = 4 KB / 回）ではなくレイテンシ（ホスト経由のコピーと同期）が支配的です。ggml-vulkan は GPU 間の直接コピーを持たず（`ggml_backend_vk_cpy_tensor_async` は同じデバイス内のみ）、通信量を減らす工夫では解決しません。
- 通信量の見積もり: `-sm layer` は層の境界ごとに hidden state 1 本（0.6B で 4 KB、8B で 16 KB）をホスト経由で渡すだけで、WX 2100 の Gen2 x1（0.3 GB/s）でも 0.05 ms 前後です。RX 6400 の 4 GB に載るモデルでは分割しない、載らないモデルだけ `-sm layer -ts N/1`、が結論です。

### f. ggml-vulkan のシェーダの改善余地

ソース（`ggml/src/ggml-vulkan/ggml-vulkan.cpp`）の AMD 向けの分岐と、`GGML_VK_*` の試験から見積もりました。

- **機種の判定**は `get_device_architecture` で、RADV では WX 2100 が `AMD_GCN`、RX 6400 が `AMD_RDNA2` になります。AMD 向けの調整は少なく、次のとおりです。
  - 1 ワークグループの行数: `rm_stdq`（Q4_0 などの標準形式）は GCN で 2、ほかの AMD で 1。K-quant の `rm_kq` は GCN で 4、ほかで 2。MMVQ の `rm_stdq_int` は GCN で 4。RDNA2 に固有の指定は `soft_max` と `im2col` のサブグループ 64 だけです。
  - mat-vec のワークグループは AMD で常に 1 サブグループ（RDNA2 は wave32、GCN は wave64）です。NVIDIA / Intel にある「M が小さいとき大きいワークグループにする」分岐（`dmmv_wg`）は AMD に無く、`GGML_VK_*` では切り替えられません。
  - MMVQ（活性を Q8_1 に量子化して整数ドット積）は、AMD では k ≥ 2048 のときだけ、Q8_0 は GCN だけ、Q6_K は使いません。RX 6400 は `int dot: 1` で、1.7B Q4_K_M（k=2048 以上の op がある）で使われると思われます（`DISABLE_MMVQ` で速度が変わったことからの推定）。WX 2100 は `int dot: 0` で使えません。
- **`GGML_VK_*` と `-fa` の試験**（tg128、`-r 3`、差が ±2% 以内は誤差の範囲）:

  | 設定 | RX 6400 / 0.6B Q8_0（既定 138.0） | RX 6400 / 1.7B Q4_K_M（既定 87.2） | WX 2100 / 0.6B Q8_0（既定 46.2） |
  | --- | --- | --- | --- |
  | `GGML_VK_DISABLE_FUSION=1` | 125.0（−9%） | 82.0（−6%） | 41.4（−10%） |
  | `GGML_VK_DISABLE_ASYNC=1` | 133.7（−3%） | 83.9（−4%） | 45.4（−2%） |
  | `-fa 0` | 129.3（−6%） | 83.3（−4.5%） | 43.0（−7%） |
  | `-fa 1`（既定は auto） | 140.7 | 87.2 | 46.0 |
  | `GGML_VK_FORCE_MMVQ=1` | 132.1（−4%） | 87.5 | 46.2 |
  | `GGML_VK_DISABLE_MMVQ=1` | 138.8 | **89.4（+2.5%）** | 45.9 |
  | `GGML_VK_MAX_NODES_PER_SUBMIT=400` | 139.3 | 87.3 | 46.0 |
  | `GGML_VK_DISABLE_MULTI_ADD=1` | 139.4 | 87.7 | 46.2 |

  既定を上回った設定は、1.7B Q4_K_M の `DISABLE_MMVQ`（+2.5%、1 回の計測）だけです。融合（FUSION）と非同期（ASYNC）、flash attention は、有効にしておくことで効いています。HARDWARE.md の「設定を変えても既定を上回らなかった」と合います。
- **残りの伸びしろ**（RX 6400 の 0.6B Q8_0、1 トークン 7.25 ms の中）:

  | 項目 | 見込み | 根拠 |
  | --- | --- | --- |
  | mat-vec の帯域効率 88% → 95% | 約 0.4 ms | 小さい行列（m=1024）が 101〜104 GB/s と低い |
  | 小さい op（norm、rope、set_rows、attention、GLU）の融合 | 約 0.5 ms | 3〜11 µs の dispatch が約 200 回 |
  | ホスト側（submit、フェンス） | 約 0.2 ms | |

  合計で最大 1.1 ms（15%）です。Q4_K_M のような小さい重みでは、固定費の割合がさらに大きくなります。WX 2100 は小さい op に 3.8 ms/token かかっており（RX 6400 の約 3.5 倍）、融合の効果が大きいはずです。
- **Q3_K の mat-vec**（上の「内訳」）: Q2_K / Q3_K 混在の 8B で最大 3.7 ms/token（11%）。
- **実装の置き場は upstream（llama.cpp）への貢献が筋**です。ggml-vulkan のシェーダに手を入れるなら、`test-backend-ops` で正しさを確認しつつ upstream へ出すと、追従の負担がなく、全 AMD GPU が恩恵を受けます。ScrapGpuLibrary の `backends/vulkan` に ggml-vulkan のシェーダを移植して手を入れると、upstream の更新を失い、得られるのは数 % から 15% 程度です。

## 4. 電力効率

- 帯域律速の範囲では、負荷中の電力はモデルの大きさにあまり依存せず（RX 6400 で 30〜35 W、WX 2100 で 24 W）、J/token は 1 トークンの時間に比例します。**速く終わる構成ほど J/token が下がります。**
- 実測で最も良い B=1 の構成は、RX 6400 の Qwen2-0.5B-ft Q4_0（0.156 J/token、200 t/s）、次が Qwen3-0.6B Q4_K_S / Q4_0（0.162〜0.163）、Q4_K_M（0.170〜0.175）です。Q8_0（0.234）より約 27% 低くなります。WX 2100 は 0.39〜0.54 J/token で、RX 6400 の約 2.5 倍です。
- **バッチ処理が最も効きます。** B=32 では 0.04 J/token 前後（RX 6400）と、B=1 の約 1/5 です（上限見積もり）。
- RX 6400 のアイドルは約 1 W、WX 2100 は約 3.2 W です。クロックと電力の設定は root が必要なので試していません。

## 5. 推奨構成

| 用途 | 構成 |
| --- | --- |
| 1 本の tg を最大にする | **RX 6400**: 公式 Vulkan の既定（`-ngl 99`、環境変数は触らない）、アプリ側で `-bs`、形式は小さいモデルなら Q6_K か Q5_K_M（品質重視）または Q4_K_M（速度重視）。1.7B Q4_K_M に限り `GGML_VK_DISABLE_MMVQ=1` が +2.5%（要再現確認）。8B クラスは Q2_K / Q3_K_S が 1 枚に載る範囲（Q3_K_S は 23.8 t/s）で、同じ GPU に 0.6B のドラフトを載せる投機的デコードが 1.31 倍。**WX 2100**: 同様に `-bs`、Q4_K_M か Q4_0 |
| 合計スループット | `llama-server -np` / `llama-batched-bench` で B=4 または B ≥ 32（RX 6400 は B=16 を避け、WX 2100 は B=8 を避ける）。`-c` は実際に必要な分（B × 系列長）に絞る。採点のような用途は、トークンごとに生成せず全トークンを 1 回で流すプロンプト処理の形にする（RX 6400 の 0.6B で約 2400〜2700 t/s） |
| 1 枚に載らないモデル | `-dev Vulkan0/Vulkan1 -sm layer -ts N/1`（N は RX 6400 に入る最大。8B-ft Q4_K_M で 8/1、14.1 t/s）。`-sm row` は Vulkan で不可、`-sm tensor` は使わない |
| 2 枚の使い分け | WX 2100 をドラフトにするのは遅くなる（0.25〜0.65 倍）ので避ける。2 枚の合計を取りたいなら、別々のプロセスで別々のモデル / 要求を処理する（GPU を共有しない） |
| 電力効率 | RX 6400 で小さい Q4 系 + `-bs` + バッチ処理（B=32 で 0.04 J/token 前後） |

## 6. ScrapGpuLibrary で取り組む価値（優先順位）

1. **何も作らず、`-bs` と形式の選択を使う**（効果 +4〜12% と +17〜28%）。GPU 側のサンプリングは llama.cpp にあり、Vulkan で動きます。使い方を README / HARDWARE.md に書くだけでよい。
2. **バッチ処理の利用側の設計**（tb250-distill の Teacher）。採点をプロンプト処理の形に寄せると、tg の 1 本より約 18 倍の速度が出る。ScrapGpuLibrary のライブラリとしては、Vulkan 用の評価（logprob）の API やスクリプトの形で支援できるが、本体は llama.cpp のままでよい。
3. **upstream（llama.cpp）への貢献**: 優先は (1) Q3_K の mat-vec（RDNA2 で 80〜86 GB/s、他形式は 111〜126 GB/s。8B Q2_K で最大 11%）、(2) AMD の小さい op の融合（RX 6400 で最大 15%、WX 2100 でより大きい）、(3) MMVQ の選択（RDNA2 の k ≥ 2048 での効果の確認）、(4) WX 2100 の B=8 付近の谷。変更ごとに `test-backend-ops` と、RX 6400 / WX 2100 以外での無劣化の確認が必要で、時間がかかる。次の一手は、`GGML_VK_PERF_LOGGER` を各形式で取り直し（小さい op のロガーの歪みを避けるため、8B クラスで）、Q3_K のシェーダ（`mul_mat_vec_q3_k.comp`）の行数（`rm_kq` を RDNA2 で 2 から 4）などを試すこと。
4. **ScrapGpuLibrary の `backends/vulkan`（ggml-vulkan のシェーダの移植）**: ggml を使わない経路（standalone C API、PyTorch / ONNX Runtime adapter）で Vulkan が必要になってから。現時点の優先度は低い。
5. **GPU 間の転送（multi-GPU transport）**: `-sm layer` で足りる。テンソル分割は PCIe のレイテンシで成立しない。

## 計測の限界

- WX 2100 / RX 6400 とも、1 回ずつの計測が多く（`-r 3〜5` の平均）、±3% 程度の差は誤差です。tg(A) と tg256 の差（0.6B Q4_K_M の RX 6400 で 181.5 と 169.2）のように、GPU のクロックの立ち上がりで 5〜7% ずれることがあります。
- KLD の測定は Qwen3-0.6B-Base のみ、約 4000 トークンの文章（CL11.md と同じ）です。1.7B / 8B の形式の評価は未実施です。
- `GGML_VK_PERF_LOGGER` の GPU 時間は、小さい op で実際より長く出ます（上の注意）。
- `-sm tensor` の遅さの原因（allreduce のレイテンシ）は、1 つのモデルの逆算であり、プロファイルで確かめていません。
- 電力は GPU 単体（hwmon）で、ボード全体や CPU は含みません。
