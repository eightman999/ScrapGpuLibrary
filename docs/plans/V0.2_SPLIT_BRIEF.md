## 0. ミッション

ScrapGpuLibrary を、現在の ggml 専用 OpenCL 1.1 バックエンドから、複数の機械学習フレームワークと GPU 実行環境を接続できる、独立した汎用 Tensor / Compute Runtime に再設計・実装する。

**最重要要件は、既存の CL11 が達成した演算精度・推論性能・GPU 対応を失わないこと。**

最終的に、以下の構成を実現する。

- PyTorch / Hugging Face Transformers → ScrapGpuLibrary → GPU Backend
- llama.cpp / GGUF → ScrapGpuLibrary → GPU Backend
- ONNX Runtime → ScrapGpuLibrary → GPU Backend
- Standalone C/C++ → ScrapGpuLibrary → GPU Backend

GPU Backend は、OpenCL 1.1、将来の Vulkan / CUDA / CPU などを交換可能とする。NVIDIA 390.157 への依存をなくすことも長期目標とするが、ドライバ移行作業とライブラリ分離は別の作業として扱う。今回の主作業はアーキテクチャ分離であり、GPU ドライバそのものは改造しない。

## 1. 現状調査と遵守事項

まず以下を読み、実装とドキュメントの一致を確認する：`README.md`、`docs/ARCHITECTURE.md`、`docs/CL11.md`、`docs/HARDWARE.md`、`adapters/ggml/ggml-cl11.cpp`、`adapters/ggml/CMakeLists.txt`、`adapters/ggml/kernels/`、`adapters/ggml/tools/`、`adapters/ggml/llama.cpp/`。既存構成を把握せずに、新しい実装を一から書き直さない。

絶対に守ること：

1. 既存の CL11 カーネルと GPU 別チューニングを原則維持する。
2. OpenCL C 1.1 より新しい機能を CL11 に必須化しない。
3. 既存の `libggml-cl11.so` のプラグイン方式を維持する。
4. 既存 llama.cpp b11384（`0faee50`）との互換性を保つ。
5. ggml / PyTorch / ONNX に依存する型を共通コアの公開 API に混入させない。
6. CPU フォールバックを明示し、性能低下を隠さない。
7. 各段階でビルド、正確性、性能の回帰試験を実施する。
8. 既存の Git 履歴、ベンチマーク、モデル、テストデータを破壊しない。
9. sudo、カーネルモジュール操作、ドライバ切り替え、GPU のクロック変更を行わない。
10. 調査・設計文書の作成だけで終了せず、通過したゲートの範囲で実装とテストまで行う。

機能追加を急ぐよりも、既存の正しさを維持することを優先する。

## 3. レイヤーの責務

**A. Core Runtime**：デバイス識別と能力情報、バッファとメモリ所有権、Tensor の論理表現、型・ストライド・ビュー、演算の意味と検証、バックエンド選択、コマンド実行と同期の共通契約、明示的な CPU フォールバック、エラー伝播。`cl_mem` / `cl_context` を公開 API に露出しない、`ggml_tensor` や `at::Tensor` を Core の基本型にしない、ベンダー固有 API を直接呼ばない。実装は C++17、外部向けには `scrapgpu_` 接頭辞の C ABI（C++ 内部実装と分離し、公開 ABI のバージョンを管理する）。

**B. Backend**：デバイス初期化、実メモリ確保・解放、メモリ転送、カーネルのコンパイルと投入、固有の同期、実行可能な演算・型・レイアウトの報告、GPU 別最適化とチューニング。まず既存 CL11 を移設する。`backends/opencl11` は OpenCL 1.1 の API だけで動作すること。OpenCL 3.0 ICD 上で動く場合も、使用機能は 1.1 として扱う。Vulkan / CUDA の新規バックエンドは今回の対象外。

**C. Adapter**：フレームワーク固有テンソルと ScrapGpu Tensor の変換、dtype / shape / stride / layout の翻訳、演算要求・グラフの翻訳、メモリ所有権と寿命の調整、固有のエラー・同期処理。Adapter に GPU カーネルを複製しない。**ggml と PyTorch は同じ ScrapGpu の演算実装を利用する。** 依存方向は Adapter → Core → Backend で、逆方向を禁止する。

## 4. バックエンド契約を先に固定する

`docs/ARCHITECTURE.md` の 8 概念（Device、Buffer、TensorDesc、PhysicalLayout、Pack / Unpack、Command / Stream、Op、KernelVariant）を具体的な API にする。

- **Device**：GPU 世代、メモリ容量、単一確保上限、ワークグループ上限、ローカルメモリ、対応演算型、ドライバ情報、既知の不具合、チューニングプロファイル。ハードウェア能力とドライバの対応機能を分けて記録する。
- **Buffer**：ハンドルとバイトオフセットで参照する。デバイス所有権、アラインメント、有効範囲、転送方向、寿命を明示する。CL11 の分割確保、単一確保上限、32bit オフセット制限を維持する。複数バッファを仮想的に一つとして扱う場合は、対応演算と制限を明示する。
- **TensorDesc**：論理 shape、stride、dtype、device、offset。量子化テンソルは論理 dtype とデバイス物理配置を別管理する。
- **PhysicalLayout**：Contiguous、Strided、R32 などを区別する。レイアウト変換は明示的な操作にし、不要なコピーや全量逆量子化を発生させない。
- **Command / Stream**：同期実行と非同期実行を表現できる設計にする。初期実装は OpenCL の in-order queue でよい。「全グラフ投入後に同期する」挙動を維持し、ノード単位の `clFinish` を追加しない。
- **Op / KernelVariant**：演算の意味、入力条件、出力条件、サポート型、精度許容値、実行候補を定義する。非対応の場合は理由を返し、暗黙のデータ転送を行わない。演算選択・CPU フォールバック・実行回数をログで確認できるようにする。

## 5. 既存最適化の保護

最重要の保護対象：Q4_0 / Q8_0 / Q4_K / Q6_K の R32 再配置、Fermi / Kepler 別チューニング、Fermi の denormal products、定数メモリによる mat-vec、Kepler の定数メモリ不具合回避、128bit coalesced load、K / V cache 用カーネル、`RMS_NORM` などの融合、複数 `MUL_MAT` の融合、`SET_ROWS` の融合、不要な `CONT` の省略、大きなテンソルのバッファ分割（加えて、MoE 用の `MUL_MAT_ID` の生成時カーネル、Mesa 向けの `split_programs`、AMD の `mad`、遅延確保のプローブ）。これらを単純な汎用実装に置き換えることは禁止する。

既存の fusion は ggml のグラフ情報に依存する部分がある。Core 側に最小限の `Graph` / `ExecutionPlan` の概念を設け、将来 PyTorch や ONNX からも融合を要求できるよう設計する。初期段階で巨大な汎用グラフコンパイラを作らない。

## 6. 段階的な実装計画

### Phase 0：現状の固定と回帰基準の取得

コードを移動する前に：現行 HEAD・ビルド構成・対応モデル・GPU 環境を記録、既存テストとベンチマークの実行方法を整理、`docs/BASELINES.md` を作成、関数単位の依存関係と移設候補を作成、CPU / GPU の比較試験を再実行可能にする。基準測定ではモデル SHA、量子化形式、コマンド、GPU、ドライバ、温度、反復回数を保存する。

**Gate 0：基準と再現手順が固定されるまで、大規模なコード移動を開始しない。**

### Phase 1：Backend Contract の設計（P1.5）

`docs/API_CONTRACT.md` を作成し、Core / Backend のインターフェースを決定する。最低限のハンドル、構造体、enum、エラー型、能力照会、同期規約を宣言する。既存カーネルや演算結果は変更しない。コンパイル可能な最小ヘッダと契約テストも用意する。成果物：API Contract、ABI バージョン方針、依存方向の検証、責務分担表、移設手順。

**Gate 1：CL11 の現在の機能がすべて表現でき、ggml の型を Core API に要求しないこと。**

### Phase 2：OpenCL Runtime 分離（P2）

`ggml-cl11.cpp` から、デバイス列挙と情報取得、OpenCL context、program build、kernel dispatch、Buffer と allocator、メモリ転送、同期・プロファイリング、GPU 別チューニングを切り出す。既存カーネルは原則そのまま移動し、演算アルゴリズムや量子化レイアウトは変更しない。依存関係は `scrapgpu_core`（OpenCL 非依存）、`scrapgpu_opencl11`（OpenCL 1.1）、`ggml-cl11`（上記を使う ggml プラグイン）。ツリー外プラグインとツリー内ビルドの両方を維持する。

**Gate 2：性能 ±3% を目標に、既存精度試験を通過すること。悪化した場合は原因を特定するまで次へ進まない。**

### Phase 3：Tensor / Quant / Ops 分離（P3）

`cl11_td`、`cl11_fastdiv_init`、`cl11_bcast`、`cl11_rp_*`、`cl11_op_*`、`cl11_supports_op_impl` を移設する。演算の意味（Core）と GPU カーネル実装（Backend）を分ける。R32 の Pack / Unpack は ggml 非依存にし、部分読み書き、量子化ブロック境界、ビューの制約を必ず試験する。既存の CPU フォールバック動作を維持する。

**Gate 3：ggml 以外の利用者から Tensor と演算 API を呼び出せること。**

### Phase 4：Standalone API の実証

ggml に依存しない小さなテストプログラム：GPU 列挙、GPU メモリ確保、CPU → GPU → CPU 転送、FP32 行列積、Q8_0 の量子化 mat-vec、同期、CPU 参照との誤差比較、リソースの解放、連続実行とエラーパス。経路は `Standalone → ScrapGpu Core → CL11 → OpenCL ICD → GPU`。

**Gate 4：ggml への依存なしに、既存 CL11 の主要計算資産を呼び出せること。**

## 7. PyTorch 対応ロードマップ（今回は設計のみ）

**Stage A：Custom Ops**（`torch.ops.scrapgpu.matmul`、`quant_matmul` など。`torch.library` / `TORCH_LIBRARY`、スキーマ、aliasing、FakeTensor を整理。CPU Tensor を受け取る最小構成から始めてよいが、GPU Tensor のネイティブ対応とは呼ばず、ホスト転送のコストも測る）。**Stage B：PrivateUse1**（独自 Device、Tensor 生成とメモリ管理、DeviceGuard、必要な ATen 演算、転送、Stream / 同期、明示的な fallback、必要に応じて Autograd、Transformers の推論）。PyTorch のバージョンを固定し、公式ドキュメントに照らして設計する。推論専用を先行する。R32 の量子化重みは全量を FP32 に展開せず GPU で直接実行する経路を優先する。GT 430 の小容量 VRAM を考慮し、F32 モデルを無条件に全層 GPU 配置する設計は避ける。

## 8. GGUF と safetensors

GGUF は当面 llama.cpp / ggml のローダーを利用する。safetensors は将来の独立ローダー、または PyTorch / Transformers 側から利用する。Tokenizer とモデルアーキテクチャは GPU Backend の責務に含めない。GGUF ローダーを不要に再実装しない。safetensors を読めることと `model.to("scrap:0")` が動くことは別の達成条件とする。

## 9. ドライバ非依存性とセキュリティ

長期的には NVIDIA 390 系を廃止し、nouveau / Mesa 等の保守されるドライバで Fermi を利用する。ドライバと Compute Runtime の責務を分離する。GPU API の抽象化をドライバの脆弱性対策と混同しない。CL11 が OpenCL 3.0 ICD 上で動くことと、GT 430 を nouveau で動かせることを区別する。nouveau 対応は別の検証環境で段階的に試す。ソース公開だけをもって安全性が保証されたとは判断しない。390 系は、必要なら隔離された性能・精度比較環境としてのみ使用する。今回はドライバのインストール、削除、切替、カーネル変更を行わず、将来の検証については実験計画と復旧手順の文書化に留める。

## 10. 回帰試験と性能基準

既存の `test-backend-ops`、`attn_check`、`mvm_check`、`llama-bench`、greedy、KL divergence を利用する。対応ケース数（冒頭の注記を参照）は「サポート対象ケースの件数」であり、ggml の全演算に対応済みという意味ではない。既存の非対応演算を、試験を通すためだけに「対応」と偽装しない。

正確性：op 単体は CPU 参照との誤差、logits は平均・分位の KL divergence と top-1 一致率（許容値はモデルと文章ごとに公式バックエンドで校正する）、PPL、greedy は補助、NaN / Inf と推論崩壊は必須検査。Q4_K 系は greedy の完全一致だけを合否基準にしない。

性能：pp128 / tg64、使用 VRAM、カーネル投入回数、転送量、同期回数、モデルロード時間、kernel launch overhead。同一機材・設定で複数回測定し中央値を比較する。通常のリファクタリングは **±3% 以内**を合格目標とする。新しい CPU コピー、全量逆量子化、隠れた同期、余計な kernel launch による悪化は原則不合格。TB250 では GPU 排他ロック（`flock ~/bench/gpu-bench.lock`）と温度制限（85 ℃）を尊重する。実機が使えない場合は未検証として残し、推定値で埋めない。

## 13. Go / Revise / No-Go 判定

各段階の終了時に判定する。**Go**：既存のテスト、精度、性能、互換性を維持できた。**Revise**：動作するが性能低下、テスト不足、抽象化の不備、依存関係の混入がある（原因を修正して再評価）。**No-Go**：既存モデルが動かない、数値精度に重大な異常、重要な最適化が失われた、または大幅な性能劣化を回避できない（失敗した変更を切り離し、直前の安定状態を保持）。大きな問題を抱えたまま次段階へ進まない。

## 14. 今回の実行範囲と最終報告

Phase 0 の調査、Phase 1 の API Contract の確定、Phase 2 の Runtime 分離の実装。ゲートを通過したら Phase 3 に進んでよい。PyTorch PrivateUse1、Vulkan、CUDA、新 GPU ドライバ、独立したモデルローダーの本格実装は対象外。最終報告：実装した内容とコミット、変更ファイル、依存関係の変化、ビルド・テストの結果、性能の before / after、未検証事項、既知の問題、次の段階に進めるかの Go / Revise / No-Go 判定。

**最終目標は CL11 を捨てることではない。CL11 で完成させた演算・量子化・最適化資産を、ggml 以外の ML フレームワークでも使える形に進化させることである。**
